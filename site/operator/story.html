The first day of running an instance, in order. Install, log in, change the password, configure OpenID Connect, give a colleague a role and a Producer to maintain, allow a webhook receiver and test a hook, set retention, take a backup and know how to restore it, read the audit log and point Prometheus at the metrics. Every exchange was recorded against a fresh 2.6.0 instance by scripts/record-walkthroughs.sh, after the payments team's story had filled its catalog; the Helm render and the restore are command transcripts, labelled as such, because no cluster was involved.

How to read this page

Previous, Next, the step chips or the arrow keys move through the steps; #step-N in the address opens one directly. Session tokens are redacted and the instance's address is shown as https://sanshain.corp; everything else is as the service answered it. The recording instance runs SQLite (the snapshot step needs it); the chart is rendered for PostgreSQL, the install the deployment chapter recommends.

5. The webhook allow-list

    

      A fresh install sends nothing: hooks may only point at hosts the administrator approved. The
      operator allows Slack and, with the http:// prefix, a plain-HTTP receiver inside
      the cluster. The recording's receiver was a small local server; the text shows it as
      receiver.sanshain.svc, the screenshots show its real address,
      http://127.0.0.1:18080.
    

    

    
What to notice

    
    
      
  • 
        A pattern is a host name with * and ?; ports are not matched; the
        list comes back trimmed and lower-cased.
      
    • 
      
  • 
        The list binds maintainers. A hook registered by an administrator is exempt from it, for
        good, and the listing marks it so.
      
    • 
      
  • It is checked again at every delivery: removing a host stops deliveries to it.
    •

Behind the story



  The single tasks of this story, and the ones it leaves out (rotate a secret, redeliver, pause a
  hook, delete a version), are the
  Operator recipes. To re-record both stories against a newer release,
  run just record-walkthroughs in the repository: it builds the service, starts a fresh
  instance on a free port with a temporary database, replays every step, compares every answer with
  what the step expects, and overwrites site/evidence/.
