Builds do not call curl. Each client reads sanshain.yaml and speaks the same contract; what differs is how it is installed and invoked. This chapter gives the shape of each one and links its own documentation, which stays the authority for flags and edge cases.

What every client has in common

  • Compatibility: client 2.x speaks Sanshain Service 2.x. The catalog push and format: openapi need Sanshain Service 2.4.0 or later; everything else works with any 2.x service.
  • Three commands: provide, require, catalog, each a separate step.
  • The ga switch: every provide is a snapshot unless SANSHAIN_GA=true (or the client's flag) is set. No git detection anywhere.
  • Streams: SANSHAIN_TRUNK=true marks a trunk build, SANSHAIN_TAG=<branch> a sanshain-branch build. Both set, the client sends neither and warns (strict mode fails before any request).
  • Environment: SANSHAIN_URL overrides sanshainUrl, SANSHAIN_TOKEN is the bearer token, SANSHAIN_BEST_EFFORT=true turns failed calls into warnings. Boolean switches are on for true or 1.
  • Warnings: a Sanshain-Warning header is printed and the build carries on; in strict mode it fails the command with strict: Sanshain warned: <text>.
  • Caching: provides always upload (the server's no-op makes that free); requires keep the ETag in a state file and skip rewriting on 304.
  • Rejections: a 409 is printed with its proposed version; a 404 on require means the pin does not exist, a 410 that the version lacks the endpoint.
  • Unknown fields in sanshain.yaml are reported; the 1.x fields (branch, timeout, baseVersion, releaseBranches) are rejected with a migration hint.

Maven (Java, Kotlin)

paxel/sanshain-maven-plugin, artifact io.github.paxel.sanshain:sanshain-maven-plugin on Maven Central, Java 11 or later. Three goals, all bound to the initialize phase by default: 

mvn sanshain:provide     # snapshot
mvn sanshain:provide -Dsanshain.ga=true
mvn sanshain:require
mvn sanshain:catalog

Configuration comes from sanshain.yaml, overridable by Maven properties (-Dsanshain.url, -Dsanshain.token, -Dsanshain.ga, -Dsanshain.trunk, -Dsanshain.tag, -Dsanshain.strict) and by the environment; URL and token can also live in settings.xml (a <server> with id sanshain for the token). The plugin inlines local $refs and proto imports into one document before upload (combine, on by default), and picks /require-bundle automatically when an entry has two or more endpoints. configFile points it at another sanshain.yaml. Require ETags are kept in target/.sanshain-cache.json, removed by mvn clean. Its README documents the full precedence chain, strict and best-effort modes, and the openapi-generator wiring.

Rust (cargo)

paxel/sanshain-rs: the sanshain library crate and the cargo-sanshain subcommand. 

cargo install cargo-sanshain

cargo sanshain provide        # snapshot (the default)
cargo sanshain provide --ga   # immutable GA
cargo sanshain require        # download the pinned snippets
cargo sanshain catalog        # push catalog-info.yaml

The subcommand README has the flags and CI recipes; the library README has the configuration reference and the Client API for builds that embed the client.

Go

paxel/sanshain-go, a CLI and a client library under the /v2 module path: 

go install github.com/paxel/sanshain-go/v2/cmd/sanshain-go@latest

SANSHAIN_TOKEN=san_… sanshain-go provide
sanshain-go --ga provide
sanshain-go --trunk provide      # or SANSHAIN_TRUNK=true
sanshain-go --tag R1 provide     # or SANSHAIN_TAG=R1
sanshain-go require
sanshain-go catalog

--config path/to/sanshain.yaml points it at another file; strict: true in the file turns on strict mode. The README covers the failure modes, the ETag state file and the 1.x migration.

JavaScript and TypeScript, and the GitHub Action

paxel/sanshain-js: the sanshain npm package with a Node client, a CLI and a composite GitHub Action. 

npm install --save-dev sanshain

npx sanshain provide          # snapshot
npx sanshain provide --ga
npx sanshain provide --trunk  # or --tag R1
npx sanshain require
npx sanshain catalog

A "prebuild": "sanshain require" script in package.json fetches the pinned snippets before every build. Beyond the shared variables the CLI reads SANSHAIN_SERVICE_NAME, SANSHAIN_STRICT and SANSHAIN_COMPRESSION; --url wins over SANSHAIN_URL, which wins over the file.

The Action wraps the CLI. Its inputs are command (provide, require or catalog), token (or the SANSHAIN_TOKEN secret in the environment), ga, trunk, tag and working-directory: 

- uses: paxel/sanshain-js@main
  with:
    command: provide
    ga: ${{ github.ref == 'refs/heads/main' }}
    trunk: ${{ github.ref == 'refs/heads/main' }}
  env:
    SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
    SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}

Conan (C, C++)

paxel/sanshain-conan, the sanshain-conan package on PyPI, installed into the environment Conan runs in. The earlier python_requires pattern is gone. 

pip install sanshain-conan
# conanfile.py
from conan import ConanFile
from sanshainconan import Sanshain

class MyProject(ConanFile):
    def generate(self):
        sanshain = Sanshain(self)
        sanshain.require()     # runs during `conan install`
        sanshain.catalog()     # optional

Providing runs from the CLI, after the tests: sanshain-conan provide (or python3 -m sanshainconan.cli provide), with --ga, --trunk, --tag and --best-effort as flags. strict: true in sanshain.yaml turns on strict mode.

No client for your language?

The contract is eight routes: POST /provide, /provide/asyncapi and /provide/grpc; GET /require, /require/asyncapi and /require/grpc; POST /require-bundle; PUT /catalog/{systemname}. CI integration shows each of them as a curl line, and Using the API covers tokens and error shapes. api.yaml in the repository is the OpenAPI document to generate a client from.
