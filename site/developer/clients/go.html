sanshain-go is the command-line client for Go projects: it reads sanshain.yaml and calls provide, require and the catalog push. This page documents version 2.5.0 from paxel/sanshain-go. The Since column of the options table names the client version an option arrived in.

Install

go install github.com/paxel/sanshain-go/v2/cmd/sanshain-go@latest
  • The module path is github.com/paxel/sanshain-go/v2. go install needs Go 1.23.3 or later (the go directive of its go.mod).
  • Every GitHub release also carries prebuilt binaries built with the current Go: sanshain-go-linux-amd64, sanshain-go-linux-arm64, sanshain-go-darwin-amd64, sanshain-go-darwin-arm64 and sanshain-go-windows-amd64.exe. The macOS binaries need macOS 12 or later.
  • The command is sanshain-go; sanshain-go --version prints sanshain-go 2.5.0.
  • Client 2.x speaks Sanshain Service 2.x. The catalog push and format: openapi need 2.4.0 or later, the origin 2.9.0, annotations 2.13.0; against an older service the client reacts as described under Failure modes.

Commands

The form is sanshain-go [flags] <command>. Flags go before the command: the client stops reading flags at the command, and anything after it is ignored without an error, so sanshain-go provide --ga publishes a snapshot. A boolean flag takes its value with =: --ga=false works, --ga false makes false the command. Both -flag and --flag are accepted. 

export SANSHAIN_URL=https://sanshain.example.com
export SANSHAIN_TOKEN=san_…

sanshain-go provide                  # snapshot
sanshain-go --ga provide             # immutable GA
sanshain-go --trunk provide          # trunk build (or SANSHAIN_TRUNK=true)
sanshain-go --tag R1 provide         # sanshain-branch build (or SANSHAIN_TAG=R1)
sanshain-go --tickets PAY-12 --note "card refunds" provide
sanshain-go --set ID=42 provide      # fills {{ID}} in the annotations
sanshain-go require
sanshain-go catalog
sanshain-go --config deploy/sanshain.yaml require
  • provide uploads every file of every provides entry, one call per file: apiType openapi (or none) to POST /provide, asyncapi to /provide/asyncapi, proto or grpc to /provide/grpc. CRLF line endings are sent as LF. Each answer is printed as ✓ Provided <name> v<version> (<stability>): N new, N updated, N deleted endpoints, followed by one line per harvested subscription (with ⚠ when it has drift or no publisher yet; these never fail the build). An entry with retired: true is a retire of its family instead and prints ✓ Retired…, closed N trunk pin(s), released N contract(s). History and existing pins are untouched.
  • require downloads every requires entry. An entry with one endpoint uses GET /require (/require/asyncapi, /require/grpc) and writes <outputDirectory>/<serviceName>.yaml; an entry with two or more endpoints uses POST /require-bundle and writes <serviceName>_bundle.yaml. With apiType: proto (or grpc) the file ends in .proto. The directory is created, the file is written readable by the owner only, and the client prints Saved <file> to <directory>.
  • catalog sends the file named by catalogInfo as PUT /catalog/<serviceName> and prints Catalog recorded for <system> (main+dev): N resources (dev without trunk) and one line per resource. See the catalog phase for what Sanshain reads.

There is no dry run: this client never sends dry_run. A pull-request pipeline that wants the checks without storing anything calls the route with curl, see Dry runs for pull requests.

The changelog begins with 0.1.0, the first release, and names no option before that. Options marked — in the Since column are not named in the changelog: SANSHAIN_TOKEN, sanshainUrl, compression, openApiFile, provide, the requires fields serviceName, outputDirectory and endpoints, and the ignored keys. The 0.1.0 entry describes provide, require, gzip compression and bearer tokens without naming keys.

Every relative path (file, openApiFile, asyncApiFile, protoFile, outputDirectory, catalogInfo) resolves against the directory of the configuration file. The ETag state file does not; see Caching.

The 1.x fields are refused by name, at the top level and in every provide, provides and requires entry, as '<field>' is no longer supported — <hint>:

  • branch: the branch model is gone; pin an exact version on each requires entry, provides read the version from the spec file.
  • timeout: pinned versions resolve immediately and never wait; remove it.
  • baseVersion: optimistic concurrency is gone; remove it.
  • releaseBranches: stability is snapshot unless SANSHAIN_GA=true, --ga or autoGa on a trunk or tag build.

Precedence

Setting The first that is set decides
URL SANSHAIN_URL (trimmed, blank counts as unset), then sanshainUrl. There is no flag.
Token SANSHAIN_TOKEN only.
serviceName serviceName, then clientName. No flag, no variable.
Stability --ga in any form, also --ga=false; then SANSHAIN_GA when not blank (true or 1 is GA, any other value, such as no, is snapshot and also overrides autoGa); then autoGa: true with a declared stream; then snapshot.
Trunk --trunk or SANSHAIN_TRUNK: either one switches it on. The flag cannot switch the variable off; --trunk=false with SANSHAIN_TRUNK=true is still a trunk build.
Tag --tag when not blank, then SANSHAIN_TAG; both trimmed.
Best effort --best-effort (it can only switch on); then SANSHAIN_BEST_EFFORT when not empty, which overrides the file both ways (yes counts as off); then bestEffort. For a missing or broken sanshain.yaml only the flag and the variable count.
Strict strict: true in the file only, so a missing or broken sanshain.yaml is never strict.
Origin Flag, then SANSHAIN_* variable, then (build and change URL only) the runner's variables. Blank values count as unset at every step.
Placeholders --set NAME=value (a later one for the same name wins), then SANSHAIN_SET_NAME (exact case). A --set NAME= with an empty value leaves the placeholder unfilled and does not fall back to the variable.
TLS, configuration file --insecure and --config only.

Every switch read from the environment (SANSHAIN_GA, SANSHAIN_TRUNK, SANSHAIN_BEST_EFFORT) is on for true or 1, trimmed and case-insensitive, and off for anything else.

Stability and streams

The rule itself is in How stability is decided; this client applies it as listed under Precedence. Every provide is a snapshot unless the ga switch or autoGa says otherwise. Publishing GA needs the releaser role; a GA provide that changes the spec without a version bump fails with 409 and the proposed version. 

sanshain-go --trunk provide          # main graph; GA with autoGa: true
sanshain-go --tag R1 provide         # sanshain-branch R1; GA with autoGa: true
sanshain-go --ga=false --trunk provide   # trunk, but a snapshot despite autoGa
  • The stream applies to provide and require; catalog sends trunk only, so a tag build's catalog push updates the dev graph alone.
  • Trunk and a tag together: the client prints ⚠ trunk and tag are mutually exclusive - this build is recorded in neither and sends neither. With autoGa: true such a provide is still GA, since a stream was declared. Under strict mode the command fails before any request.
  • An unknown tag is recorded in no release graph; the call succeeds and Sanshain's warning is printed (see Strict mode and best effort).
  • A retire carries no stability and no stream, autoGa or not.

Origin

Only provide sends an origin. The runner variables the client reads on GitHub Actions, GitLab CI and Jenkins, and what Sanshain does with the fields, are in Why: the origin of a build. 

sanshain-go --tickets ORD-7,ORD-9 --note "Adds the users endpoint" provide
  • --build-url / SANSHAIN_BUILD_URL and --change-url / SANSHAIN_CHANGE_URL override the runner's variables. On other CI systems set the two variables yourself.
  • --tickets / SANSHAIN_TICKETS is split at commas; ids are trimmed, empty ones dropped, duplicates sent once. --note / SANSHAIN_NOTE is one line. Neither comes from the runner.
  • An empty field is left out of the call. Nothing is read from git.
  • A service before 2.9.0 refuses the origin; the client prints ⚠ Sanshain Service before 2.9.0 does not take the build's origin; providing without it on stderr and repeats the provide without it.

Annotations

The file's side, the limits and what Sanshain shows are in Annotations. This client checks each entry before any request: exactly the strings scope (version or system), name and value, or it stops naming the entry, for example annotations[0] (requirements): missing 'value'. 

sanshain-go --set AREA=7 --set ID=42 provide
# or
SANSHAIN_SET_AREA=7 SANSHAIN_SET_ID=42 sanshain-go provide
  • A placeholder is {{NAME}} with letters, digits and _ only; {{ A }} or {{a-b}} stays literal text. --set splits at the first =, so the value may contain more.
  • An entry with an unfilled placeholder is left out and the others are sent: ⚠ annotation 'requirements' left out: {{ID}} is not set (--set ID=… or SANSHAIN_SET_ID). The check runs for every command, also for an entry the command would not send.
  • provide sends both scopes; require (the annotations query parameter), the bundle and catalog send the system entries; a retire sends none.
  • A service before 2.13.0 refuses them; the client repeats the call without them, sends none for the rest of the run and prints once on stderr ⚠ Sanshain Service before 2.13.0 does not take annotations; sending without them.

Caching

  • Requires keep the ETag of each answer in .sanshain-cache.json in the working directory, not next to sanshain.yaml. It is JSON, readable by the owner only: {"requires": {"<key>": {"etag": "…", "last_fetched": "<UTC time>"}}}.
  • The key is producer|version|METHOD|path for one endpoint and producer|version|bundle for a bundle, then |format=openapi when a format is asked for, then |out=<outputDirectory>, the output directory as resolved next to sanshain.yaml, so the same endpoint required into two directories is written to both.
  • The next require sends If-None-Match, unless the output file is missing; then the answer is written again. On 304 the client prints ⏭ <serviceName> spec unchanged (304), skipping code generation. and writes nothing. The entry is written after a file was saved, only when the answer carried an ETag.
  • There is no clean command. Delete .sanshain-cache.json, or the downloaded file, to force a download.
  • Provides are not cached: every provide uploads, and an identical upload is a no-op on the server.

Strict mode and best effort

Strict mode is switched on by strict: true in sanshain.yaml and nothing else. Without it, missing configuration warns and the command exits 0:

  • ⚠ No serviceName configured. Skipping provide. Set strict: true to fail in this case. (also require, catalog)
  • ⚠ No provide configuration found in sanshain.yaml. Skipping. Set strict: true to fail in this case.
  • ⚠ No requires configured in sanshain.yaml. Skipping. Set strict: true to fail in this case.
  • ⚠ No catalogInfo in sanshain.yaml - skipping catalog.

Under strict mode these fail instead, with serviceName is required (in sanshain.yaml or via environment), no provide configuration found in sanshain.yaml, no requires configured in sanshain.yaml and strict: sanshain.yaml has no catalogInfo (the catalog checks only serviceName and catalogInfo). Strict mode also fails on:

  • Unknown fields: the notice ends in rejected (strict) and the command fails with Error: strict: sanshain.yaml has unknown fields. Under best effort only when the file otherwise loads; a file that does not is broken (see below), and the notice ends in ignored.
  • Trunk and tag together: Error: strict: trunk and tag are mutually exclusive - this build is recorded in neither, before any request.
  • An unfilled placeholder: Error: strict: annotation '…' left out: …, before any request.
  • A Sanshain-Warning on any answer: Error: strict: Sanshain warned: <first warning>, right after the call. Without strict mode each warning is printed as ⚠ <text> and the build goes on. The two "Sanshain Service before …" notices are not Sanshain warnings and never fail.

Best effort is switched on by --best-effort, SANSHAIN_BEST_EFFORT=true or bestEffort: true (see Precedence). A failed call (an error status, a network error) or an unreadable spec or catalog file then prints Warning: <error>, and the command goes on with the next provides or requires entry and exits 0.

A sanshain.yaml that is missing, cannot be read or does not load (invalid YAML, 1.x fields, invalid entries, an unsupported apiType) fails the command with Error loading config: <error> without best effort; a missing file is named, as in failed to read config file: open sanshain.yaml: no such file or directory. With --best-effort or SANSHAIN_BEST_EFFORT=true it prints Warning: <error>, calls nothing and exits 0 (since 2.5.0; before, it printed Warning loading config: <error> and a skip notice). Such a file's own bestEffort and strict do not count.

Best effort never softens any strict failure above: missing configuration in every command, unknown fields in a file that otherwise loads, trunk and tag together, unfilled placeholders and Sanshain warnings.

Failure modes

The client prints Error: <message> and exits 1, or with best effort Warning: <message> and exits 0. A malformed flag, such as --set AREA without =, exits 2 with the usage. Messages and ⚠ lines go to stdout; only the unknown-field notice and the two "Sanshain Service before …" notices go to stderr.

Situation What the client does
409 on provide with a proposed version <server message> and Publish as <version> — update info.version in <file> and re-run (for proto: the // sanshain-version comment). The spec file is never changed. Exit 1.
403 on provide provide refused (403): <message>. When the service refused for want of the releaser role, it adds that publishing GA requires the role, or to publish a snapshot by leaving --ga / SANSHAIN_GA unset and autoGa off (or setting SANSHAIN_GA=false). Any other 403, such as a read-only token's (which needs scope full), shows the service's message alone. Exit 1.
403 or 404 on a retire retire refused (403): …, naming the releaser role or a maintainer grant on the Producer when the service refused for want of the role (any other 403 shows the service's message alone); retire failed (404): … when nothing was ever provided under that name.
404 on require (Unknown) failed to require <name>: unknown producer or version (404): … — the pin <name>@<version> does not exist on the server; fix the version in sanshain.yaml (list available: GET /producers/<name>/versions). Exit 1, nothing waits.
410 on require (Absent) failed to require <name>: endpoint absent (410): version <version> of <name> exists but deliberately lacks the requested endpoint(s): …. Exit 1.
No token, 401, any other error status The client does not check the token; the server's answer is printed as request failed with status <code>: <body> (body cut at 1000 characters). Exit 1.
Network error The Go HTTP error, e.g. Post "…/provide": dial tcp …; on require prefixed failed to require <name>: . Exit 1.
Pre-2.0 server After a failed answer the client asks GET /version once and reports Sanshain server at <url> is <version>; this client requires Sanshain 2.x — upgrade the server. Exit 1.
Service before 2.4.0: catalog A 404 on the push is reported as sanshain catalog needs Sanshain Service 2.4.0 or later (server is <version>). Exit 1.
Service before 2.4.0: format: openapi A refused parameter or an AsyncAPI answer is reported as format: openapi needs Sanshain Service 2.4.0 or later (server is <version>); nothing is written. Exit 1.
Service before 2.9.0: origin; before 2.13.0: annotations The call is repeated without them, with a notice on stderr (see Origin, Annotations). The command succeeds.
Catalog file not readable as the system's Component Sanshain records nothing; its warning is printed (or ⚠ Sanshain did not record <file>) and the command exits 0, 1 under strict mode.
Unknown field in sanshain.yaml On stderr, once per run, before the other configuration errors (only a 1.x field is reported earlier): 
   /\_/\  ?
  ( O_o )   sanshain.yaml: unknown field 'catalogInf' - ignored
 ---U-U---
Nested keys are named by path, such as provides[1].verison. The run continues; under strict mode it fails (see above), also under best effort when the file otherwise loads.
1.x field Error loading config: '<field>' is no longer supported — <hint> (prefixed with the entry, such as requires[0]: ). Exit 1, or a warning under best effort (see Strict mode and best effort).
Unsupported apiType on a provide or a require Error loading config: provide[0]: unsupported apiType: <value> — use openapi, asyncapi or proto (grpc means proto) (a require's starts requires[0] (<producer>): ). Exit 1, before any request, or a warning under best effort.
Invalid requires entry Error loading config: … naming the entry, e.g. requires[0] (auth-service): missing 'version' — … or the format combination. Exit 1, before any request, or a warning under best effort.
Missing or unreadable sanshain.yaml Error loading config: failed to read config file: open <path>: …. Exit 1, or a warning under best effort.
Trunk and tag together ⚠ trunk and tag are mutually exclusive - this build is recorded in neither; neither is sent and the command goes on. Exit 1 before any request under strict mode.

No importable library

The client code lives in internal/ packages of the module (internal/api, internal/config, internal/cache), which Go does not let other modules import. A Go build uses the sanshain-go command; there is no Go API to call from your own code.

Wiring into go generate

go generate runs each command in the directory of the package that holds the directive, not in the module root. Pass --config with the path from that package to sanshain.yaml; the client then resolves outputDirectory against the configuration's directory. The ETag state file lands in the package directory, so add .sanshain-cache.json to .gitignore.

sanshain.yaml in the module root

serviceName: my-go-service
requires:
  - serviceName: auth-service
    version: 1.2.0
    outputDirectory: internal/api/auth
    endpoints:
      - method: GET
        path: /users/{id}

internal/api/doc.go

//go:generate sanshain-go --config ../../sanshain.yaml require
//go:generate oapi-codegen -package auth -o auth/client.gen.go auth/auth-service.yaml
package api
go install github.com/paxel/sanshain-go/v2/cmd/sanshain-go@latest
go install github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@latest
SANSHAIN_URL=https://sanshain.example.com SANSHAIN_TOKEN=san_… go generate ./...

The entry has one endpoint, so the file is auth-service.yaml; with two or more it would be auth-service_bundle.yaml. The repository's docs/integration.md has the same wiring.

CI recipes

A Producer provides after its tests; a Consumer requires before it generates code. Trunk and GA are declared on main only. Instead of setting the ga switch you can put autoGa: true in sanshain.yaml and declare trunk alone. The URL and token come from the CI system's variables and secrets.

GitHub Actions

- name: Sanshain Require
  run: |
    go install github.com/paxel/sanshain-go/v2/cmd/sanshain-go@latest
    sanshain-go require
  env:
    SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
    SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}
    SANSHAIN_TRUNK: ${{ github.ref == 'refs/heads/main' }}

# … build and test …

- name: Sanshain Provide
  run: sanshain-go provide
  env:
    SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
    SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}
    SANSHAIN_TRUNK: ${{ github.ref == 'refs/heads/main' }}
    SANSHAIN_GA: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}

The repository's own GitHub recipes, in docs/integration.md, set SANSHAIN_GA: "true" on the release pipeline or SANSHAIN_TRUNK: "true" with autoGa, and add a sanshain-go catalog step with trunk on the trunk pipeline.

GitLab CI

sanshain-require:
  image: golang:1.23
  script:
    - go install github.com/paxel/sanshain-go/v2/cmd/sanshain-go@latest
    - sanshain-go require
    # … code generation and tests
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      variables:
        SANSHAIN_TRUNK: "true"
    - when: on_success

sanshain-provide:
  image: golang:1.23
  stage: deploy
  script:
    - go install github.com/paxel/sanshain-go/v2/cmd/sanshain-go@latest
    - sanshain-go provide
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      variables:
        SANSHAIN_TRUNK: "true"
        SANSHAIN_GA: "true"
    - when: on_success

SANSHAIN_URL and SANSHAIN_TOKEN are CI/CD variables of the project (the token masked). The client takes the job URL and, in merge request pipelines, the merge request URL from GitLab's own variables.

Jenkins (declarative, multibranch)

pipeline {
  agent any
  environment {
    SANSHAIN_URL   = 'https://sanshain.example.com'
    SANSHAIN_TOKEN = credentials('sanshain-token')
    SANSHAIN_TRUNK = "${env.BRANCH_NAME == 'main' ? 'true' : ''}"
  }
  stages {
    stage('Require') {
      steps { sh 'sanshain-go require' }
    }
    // … build and test …
    stage('Provide') {
      environment {
        SANSHAIN_GA = "${env.BRANCH_NAME == 'main' ? 'true' : ''}"
      }
      steps { sh 'sanshain-go provide' }
    }
  }
}

sanshain-go must be on the agent's PATH, from go install or a release binary. The client reads BUILD_URL and, on pull request builds, CHANGE_URL by itself.

Checked against v2.13.0 and sanshain-go 2.5.0.
