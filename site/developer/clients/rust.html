cargo-sanshain is the cargo sanshain subcommand, and sanshain is the Rust library behind it. Both are at 4.0.0 and live in paxel/sanshain-rs. The two crates always share one version number. Version 4.x speaks Sanshain Service 2.x. In the tables below, the Since column gives the client version an option arrived in, as the repository's changelog names it.

Install

cargo install cargo-sanshain

Both crates need Rust 1.89 or later (edition 2024). CI builds and tests with 1.89. They are published on crates.io only; there are no prebuilt binaries. The subcommand runs as cargo sanshain and has three commands: provide, require and catalog.

A build that embeds the client, for example in build.rs, depends on the library instead:

Cargo.toml

[build-dependencies]
sanshain = "4"

Which service version each part needs:

  • The catalog push and format: openapi need Sanshain Service 2.4.0 or later.
  • The origin of a provide needs 2.9.0, and annotations need 2.13.0. An older service refuses those fields; the client then repeats the call without them and warns.
  • Everything else works with any 2.x service.

Commands

cargo sanshain provide                  # snapshot (the default)
cargo sanshain provide --ga             # immutable GA
cargo sanshain provide --trunk          # trunk build; GA as well with autoGa: true
cargo sanshain provide --tag Release-Maribou --ga
cargo sanshain require                  # download the pinned snippets
cargo sanshain require --trunk
cargo sanshain catalog --trunk          # push catalog-info.yaml
cargo sanshain provide --set AREA=7 --set ID=42
cargo sanshain --best-effort require    # --best-effort may also follow the command

--best-effort is the only global flag: it may come before or after the command. Every other flag belongs to its command and goes after it. --trunk, --tag and --set exist on all three commands. --ga and the origin flags exist on provide only. There are no short forms, apart from -h/--help and -V/--version.

The subcommand always reads sanshain.yaml from the working directory. There is no option that names another file, so run it from the directory that holds the file. Relative paths in the file resolve against that directory.

  • provide publishes every provides entry under the version declared in the spec file. It normalizes line endings to LF first. An entry marked retired: true retires that API family instead; its file does not have to exist. The command prints Providing <file> as '<serviceName>' (<stability>)... and then Stored version <v> (<stability>): N inserts, N updates, N deletes [<hash>]. AsyncAPI provides also list the harvested subscriptions; one with drift or without a publisher yet is printed as a warning. The command never sends dry_run: a pull-request check calls the route with curl, as in Dry runs for pull requests.
  • require downloads every requires entry. An entry with one endpoint uses GET /require, /require/asyncapi or /require/grpc. Two or more endpoints arrive as one merged document through POST /require-bundle. The file is written to <outputDirectory>/<serviceName>.yaml, or .proto for apiType: proto (or grpc), and the directories are created. Give each entry its own outputDirectory: two entries for the same Producer in one directory write the same file.
  • catalog pushes the file named by catalogInfo with PUT /catalog/<serviceName>. It prints Catalog recorded for <system> (main+dev): N resources ((dev) off trunk), followed by one line per resource. See The catalog phase for what Sanshain reads.

Every call goes straight to the server. Proxy variables in the environment (HTTP_PROXY, http_proxy, ALL_PROXY, …) are ignored. A connection attempt times out after 30 seconds, and at most 5 redirects are followed. There is no option for a custom CA and none for skipping certificate checks.

The changelog begins with 2.0.0, the release that added the library and the subcommand for Sanshain Service 2.x. Options marked 2.0.0 date from that first entry; 1.x is not covered. Where Since is —, the changelog does not name the option.

A field that no Sanshain client knows, such as a typo like catalogInf, is reported once per run and otherwise ignored (see Failure modes). The fields of the 1.x clients are refused before any request, each with a hint:

  • branch: replace it with an exact version pin.
  • timeout: remove it; pins resolve immediately.
  • baseVersion/base_version: remove it; the version comes from the spec file.
  • releaseBranches/release_branches and stability: snapshot is the default, and GA is SANSHAIN_GA=true or --ga.
  • spec_id: specs are addressed by serviceName and the pinned version.
  • api_key: pass the token as SANSHAIN_TOKEN.
  • service_url: use sanshainUrl or SANSHAIN_URL.

The file is read as YAML 1.2. Only true and false are booleans, so yes or on stays text, and a duplicate key is an error. Merge keys (<<: *anchor) work. Write each pin in full, such as version: 2.3.0. A bare number like version: 2 is refused.

Precedence

The boolean variables count as on for true or 1, in any case and with surrounding whitespace ignored.

Setting Order, first that is set wins
Server URL SANSHAIN_URL, then sanshainUrl; neither is an error. A SANSHAIN_URL that is set but empty still counts as set and hides sanshainUrl, so leave the variable unset instead.
Token SANSHAIN_TOKEN only; nothing in the file, no flag.
serviceName The file only.
Stability --ga; then SANSHAIN_GA unless it is blank (any other value decides either way, so false beats autoGa); then autoGa: true on a build that declares a stream; then snapshot. --ga can only switch GA on.
Trunk On when --trunk is given or SANSHAIN_TRUNK is on. --trunk cannot switch SANSHAIN_TRUNK off.
Tag --tag, then SANSHAIN_TAG. The value is trimmed, and a blank one declares no tag. A given --tag, even a blank one, hides SANSHAIN_TAG.
Best effort --best-effort (it can only switch on); then SANSHAIN_BEST_EFFORT unless it is empty (any other value decides either way); then bestEffort.
Strict SANSHAIN_STRICT unless it is empty (any other value decides either way, so SANSHAIN_STRICT=false turns off strict: true); then strict. There is no flag.
Origin, per field The first non-blank value, trimmed: the flag, then the SANSHAIN_* variable, then, for the two URLs only, the runner's own variables. A blank flag or variable falls through to the next source.
Placeholder {{NAME}} The last --set NAME=…, then SANSHAIN_SET_NAME (exact case). An empty value leaves it unfilled; an empty --set does not fall back to the variable.

Stability and streams

Every provide is a snapshot unless the build switches it to GA. It can do that with --ga, with SANSHAIN_GA=true, or with autoGa: true in sanshain.yaml on a build that declares a stream. The rule is in How stability is decided. Nothing is read from git. Publishing GA needs the releaser role. A retire never carries a stability, whatever autoGa says.

  • Trunk (--trunk, SANSHAIN_TRUNK) works like this: provides and bundles carry trunk: true, single requires carry trunk=true, and the catalog push carries trunk: true.
  • Tag (--tag, SANSHAIN_TAG) names a sanshain-branch, which goes into provides, bundles and requires. The catalog push never sends a tag, so a tag build's push updates the dev graph only.
  • Both declared: the build sends neither and prints warning: trunk and tag are mutually exclusive - this build is recorded in neither. In strict mode it fails before any request. Under autoGa: true such a build still counts as having declared a stream, so its provides are GA.

Streams never change what is served; see Release graphs.

Origin

provide sends the origin of the build from --build-url, --change-url, --tickets and --note, or from SANSHAIN_BUILD_URL, SANSHAIN_CHANGE_URL, SANSHAIN_TICKETS and SANSHAIN_NOTE. The two URLs fall back to the runner's variables on GitHub Actions, GitLab CI and Jenkins; that table is in CI integration. Tickets and the note never come from the runner.

  • The ticket list is split at commas and each id is trimmed. Empty ids and repeats are dropped. The limits on ids, URLs and the note are checked by the service, not by the client.
  • Fields without a value are left out of the call. Requires, retires and the catalog push carry no origin.
  • A service before 2.9.0 refuses the fields. provide then repeats the provide without them and prints warning: Sanshain Service before 2.9.0 does not take the build's origin; providing without it for each spec it provides.

Annotations

The entries and what Sanshain does with them are described in sanshain.yaml, Annotations. Each entry needs the strings scope (version or system), name and value. A missing field, another type or another scope fails before any request and names the entry. An extra key is reported as an unknown field.

  • A placeholder is {{NAME}}, where NAME is made of letters, digits and _. Anything else between double braces ({{ A }}, {{a-b}}) stays literal text.
  • --set NAME=value is repeatable and splits at the first =, so the value may contain more. It exists on all three commands. SANSHAIN_SET_NAME is the fallback (see Precedence).
  • An entry with an unfilled placeholder is left out, the others are sent, and the command prints, for example, warning: annotation 'requirements' left out: {{ID}} is not set (--set ID=… or SANSHAIN_SET_ID). In strict mode the first such entry fails the command before any request, with strict: annotation 'requirements' left out: …, also under best effort.
  • Which call sends which entries:
    • provide sends every entry.
    • require sends only the scope: system ones: as the annotations query parameter for a single endpoint, in the body for a bundle.
    • catalog also sends only the scope: system ones.
    • A retire sends none.
  • A service before 2.13.0 refuses the field. The call is repeated once without it, the client sends no annotations for the rest of the run, and it prints once: warning: Sanshain Service before 2.13.0 does not take annotations; sending without them. Strict mode does not fail on this warning.

Caching

The Rust client keeps no state file and no ETag. It sends no If-None-Match, so every require downloads the full snippet and overwrites the file in outputDirectory. Provides always upload the whole spec; re-providing byte-identical content is a server-side no-op, so running provide on every build causes no churn.

Strict mode and best effort

Strict mode is on with strict: true or SANSHAIN_STRICT=true. It turns these cases into failures:

  • Missing configuration: strict: sanshain.yaml has no <what>, where the missing part is serviceName, provide/provides entries, requires entries or catalogInfo. catalog checks only serviceName and catalogInfo.
  • Unknown fields: strict: sanshain.yaml has unknown fields.
  • Trunk and a tag together.
  • An unfilled annotation placeholder.
  • Any Sanshain-Warning: strict: Sanshain warned: <text>, after the call.

Without strict, missing configuration prints No <what> in sanshain.yaml - skipping <command>. Set strict: true to fail in this case. (catalog omits the last sentence) and exits 0. Each Sanshain warning prints as warning: <text>, and the build carries on.

Best effort is on with --best-effort, SANSHAIN_BEST_EFFORT=true or bestEffort: true. A failed call (an error status, an unreachable server, a missing URL outside strict mode) is printed, followed by Continuing (best effort), and the command exits 0.

  • require carries on with the next entry and prints Error requiring <serviceName> <version>: <error>.
  • provide carries on with the next entry after a failed call, and skips a missing spec file with Spec file not found: <path>. When every file was missing, it prints No specification files found to provide. Skipping. Set strict: true to fail in this case.

Best effort never softens a configuration error: a sanshain.yaml that is missing, cannot be read or does not validate (1.x fields included) fails also with best effort. Nor does it soften strict mode: every strict failure above still fails, and so does a missing URL (strict: configuration error: missing 'sanshainUrl' — …).

The sanshain library

The sanshain crate is what the subcommand is built on. A build script or another tool calls it directly. It is blocking (no async runtime), and it does what the subcommand does except decide: strict mode, best effort and printing Sanshain warnings are left to the caller.

build.rs: require the pinned snippets before compiling

use sanshain::{CONFIG_FILE, Client, Config, Stream, fill_annotations};

fn main() -> Result<(), sanshain::Error> {
    let config = Config::from_yaml_file(CONFIG_FILE)?;
    let Some(name) = config.service_name.as_deref() else {
        return Ok(()); // no serviceName: nothing to require as
    };
    let (stream, warning) = Stream::resolve(false, None); // reads SANSHAIN_TRUNK / SANSHAIN_TAG
    if let Some(warning) = warning {
        eprintln!("warning: {warning}");
    }
    let filled = fill_annotations(&config.annotations, &[]); // SANSHAIN_SET_* only
    for warning in &filled.warnings {
        eprintln!("warning: {warning}");
    }
    let client = Client::from_config(&config)? // SANSHAIN_URL, SANSHAIN_TOKEN
        .with_stream(stream)
        .with_annotations(filled.annotations);
    for entry in &config.requires {
        let written = client.require(name, entry)?;
        eprintln!("wrote {}", written.display());
    }
    for warning in client.take_warnings() {
        eprintln!("warning: {warning}");
    }
    Ok(())
}
  • Configuration.
    • Config::from_yaml_file(path) loads and validates a file and resolves its relative paths against the file's directory. Config::from_yaml_str and Config::from_value (a serde_json::Value) skip that resolution.
    • Config::load_yaml_file and load_yaml_str return a LoadedConfig carrying unknown_fields, the file's strict and the validation result separately. puzzled_cat formats the unknown-field message.
    • The public fields of Config are sanshain_url, service_name (an Option), provides, requires, strict, best_effort, catalog_info, auto_ga, annotations and unknown_fields.
    • Config has no Default, so code that builds one lists every field. 4.0.0 added auto_ga and annotations, which is why it is a major version.
  • Client.
    • Client::from_config(&config) takes the URL and token from SANSHAIN_URL/sanshainUrl and SANSHAIN_TOKEN. Client::new(url, token) takes them as arguments.
    • Builders, set once per run: with_stream(Stream), with_origin(Origin) and with_annotations(Vec<Annotation>).
    • Calls: provide(name, &entry, Stability) returns a ProvideResponse (version, stability, content hash, changes, harvested subscriptions). retire(name, ApiType) returns a RetiredProtocol. require(name, &entry) writes the file and returns its path. catalog(name, &path) returns a CatalogResponse with recorded and the resources.
  • Deciding.
    • Stream::resolve(trunk_flag, tag) returns the stream and, for trunk plus a tag, the warning.
    • Stability::resolve(ga_flag, config.auto_ga, stream_declared) applies the order in Precedence and reads SANSHAIN_GA.
    • Origin::resolve(&OriginFlags) reads the variables and the runner.
    • fill_annotations(&config.annotations, &sets) returns the filled entries and one warning per entry left out.
    • resolve_switch_with(flag, env, configured) resolves strict and bestEffort the way the subcommand does.
    • The _with variants take the environment as an argument, for tests.
  • Warnings. client.take_warnings() hands over every Sanshain-Warning line received since its last call, from successes and failures alike; the library never prints or fails on them. Two messages are the exception: the library writes them to stderr itself. They are the origin warning (repeated for each provide on a service before 2.9.0) and the annotations warning (once per Client, on a service before 2.13.0). They are also public as ORIGIN_DROPPED_WARNING and ANNOTATIONS_DROPPED_WARNING.
  • Errors. Every call returns sanshain::Result. The Error variants are Config, Http (transport), Io, Serialization, Api (the server refused; the message is the one in Failure modes) and WrongServer (a pre-2.0 instance).

CI recipes

The steps, without a CI system around them: 

# trunk pipeline
- run: cargo sanshain require --trunk
- run: cargo sanshain provide --trunk --ga
- run: cargo sanshain catalog --trunk      # needs Sanshain Service 2.4.0+

# release-branch hotfix
- run: cargo sanshain provide --tag "Release-Maribou" --ga

The three recipes below are written for this page. Each one requires before the build and provides after it, declares trunk and GA on the default branch only, and keeps the URL and the token out of the repository. With autoGa: true in sanshain.yaml the GA line can go, because trunk alone makes those provides GA.

GitHub Actions

name: Contracts
on: push

jobs:
  sanshain:
    runs-on: ubuntu-latest
    env:
      SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
      SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}
      SANSHAIN_TRUNK: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}
      SANSHAIN_GA: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}
    steps:
      - uses: actions/checkout@v4
      - run: cargo install cargo-sanshain
      - run: cargo sanshain require      # Consumer
      - run: cargo build
      - run: cargo sanshain provide      # Producer
      - run: cargo sanshain catalog

Off main both variables are empty, which counts as unset: the build provides a snapshot and declares no stream. It is never false, which would keep a build a snapshot even under autoGa.

GitLab CI (SANSHAIN_URL and SANSHAIN_TOKEN as CI/CD variables)

sanshain:
  image: rust:1.89
  script:
    - cargo install cargo-sanshain
    - |
      if [ "$CI_COMMIT_BRANCH" = "$CI_DEFAULT_BRANCH" ]; then
        export SANSHAIN_TRUNK=true SANSHAIN_GA=true
      fi
    - cargo sanshain require
    - cargo build
    - cargo sanshain provide
    - cargo sanshain catalog

Jenkins (declarative, multibranch)

pipeline {
  agent any
  environment {
    SANSHAIN_URL   = 'https://sanshain.corp.com'
    SANSHAIN_TOKEN = credentials('sanshain-token')
    SANSHAIN_TRUNK = "${env.BRANCH_NAME == 'main' ? 'true' : ''}"
    SANSHAIN_GA    = "${env.BRANCH_NAME == 'main' ? 'true' : ''}"
  }
  stages {
    stage('Require') { steps { sh 'cargo sanshain require' } }
    stage('Build')   { steps { sh 'cargo build' } }
    stage('Provide') { steps { sh 'cargo sanshain provide' } }
    stage('Catalog') { steps { sh 'cargo sanshain catalog' } }
  }
}

A release or hotfix pipeline sets SANSHAIN_TAG (or passes --tag) instead of trunk. The origin's build and change URLs come from these runners' own variables without any configuration.

Checked against v2.13.0 and cargo-sanshain 4.0.0.
