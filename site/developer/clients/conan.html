sanshain-conan 2.5.0 is the client for Conan projects (C, C++): a Python package on PyPI with a command line tool and a helper for conanfile.py. Its repository is paxel/sanshain-conan. This page says what this client reads and how it behaves; what each sanshain.yaml field means for the service is in sanshain.yaml. The Since column of the options table names the client version an option arrived in.

Install

Install the package from PyPI into the same Python environment Conan runs in:

pip install sanshain-conan
  • It needs Python 3.11 or later. Its only dependencies are requests and pyyaml, so Conan itself is not installed with it. The helper is written for Conan 2 (from conan import ConanFile).
  • It installs one command, sanshain-conan. The same tool also runs as python3 -m sanshainconan.cli. python -m sanshainconan does not work, because the package has no __main__ module.
  • The conanfile.py helper is imported from the package. The earlier python_requires = "sanshain-conan/x.y.z" pattern was removed in 2.1.0.

conanfile.py

from conan import ConanFile
from sanshainconan import Sanshain

class MyProject(ConanFile):
    def generate(self):
        sanshain = Sanshain(self)
        sanshain.require()     # runs during `conan install`

Commands

There are three commands: provide, require and catalog. Every flag belongs to the tool, not to the command, so flags go before the command. A flag after the command is refused with a usage error (exit code 2). If no command is given, the tool prints its help and exits 1. 

# Provide the specs listed under provides (in CI, after the tests)
sanshain-conan provide
sanshain-conan --ga --trunk provide
sanshain-conan --tag release-2.4 provide

# Require the pinned endpoints listed under requires
sanshain-conan require

# Push the catalogInfo file (needs Sanshain Service 2.4.0 or later)
sanshain-conan catalog

# The same tool as a module, with another config file
python3 -m sanshainconan.cli --config build/sanshain.yaml provide
  • provide sends each provides entry to /provide, /provide/asyncapi or /provide/grpc, depending on its apiType (openapi when absent). It prints Providing <apiType> <serviceName> (stability: <stability>)..., then the summary ✓ Provided 1.4.0 (snapshot): 2 new, 1 updated, 0 deleted endpoints, and at the end Successfully provided.. The spec file is read as UTF-8 with a leading BOM removed, and CRLF line endings become LF before upload. After an AsyncAPI provide, each harvested subscription is printed as subscription <channel> / <message> <- <owner>. Entries with drift or without a publisher (<- (no publisher yet)) get a ⚠ and never fail the build.
  • A provides entry with retired: true retires its apiType family (see the provides section). The call carries no document, stability, stream, origin or annotations. The client prints ✓ Retired: cleared the '<tag>' capability, closed N trunk pin(s), released M contract(s). History and existing pins are untouched.
  • require handles each requires entry. An entry with one endpoint is a GET /require (or /require/asyncapi, /require/grpc). An entry with several endpoints is one POST /require-bundle, and the merged document is written as one file. The file is <outputDirectory>/<serviceName>.yaml, or .proto for apiType: proto or grpc (a bundle sends grpc as api_type: proto). The client writes the bytes exactly as received and creates the directory if needed. It prints Requiring N endpoints from <serviceName> (version: <pin>, type: <apiType>)... and Saved to <file>.
  • catalog pushes the file named by catalogInfo with PUT /catalog/<serviceName> (see the catalog phase). A trunk build sends trunk: true; a tag is never sent. On success the client prints Catalog recorded for <system> (main+dev): N resources (dev on a non-trunk build) and one line per resource.

Every relative path in sanshain.yaml (file, openApiFile, asyncApiFile, protoFile, outputDirectory, catalogInfo) is resolved against the folder that holds sanshain.yaml; absolute paths stay absolute. Every call times out after 30 seconds. There is no dry run: this client never sends dry_run. A pull-request check calls the route with curl as in Dry runs for pull requests.

The changelog begins at 0.1.1. Where the Since column shows —, the changelog does not name the option.

The 2.0 model removed four fields, and since 2.0.0 the client refuses them with a migration hint, whether or not strict mode is on. It checks the top level, provide, each provides entry and each requires entry:

  • branch: the branch model is gone; pin an exact version (requires) or put the version in the spec file (provides).
  • timeout: Sanshain resolves immediately; remove it.
  • baseVersion: GA immutability replaced it; remove it.
  • releaseBranches: the ga switch or autoGa on a trunk or tag build decides stability; remove it.

Every other field the client does not know (usually a typo) is reported once per run and otherwise ignored. See Failure modes.

Precedence

Setting How the client decides

serviceName serviceName, else clientName. There is no variable.
Stability The first that is set decides:
  1. --ga (it can only say GA);
  2. SANSHAIN_GA when it is not blank: true or 1 means GA, any other value (false, yes) means snapshot;
  3. autoGa: true on a build that declares a stream;
  4. snapshot.
Trunk On if --trunk is given or SANSHAIN_TRUNK is on. Omitting --trunk does not switch the variable off.
Tag --tag if it is not blank, else SANSHAIN_TAG. A blank value counts as unset.

Strict strict: true only. There is no flag and no variable.

Stability and streams

The rule itself is in How stability is decided. In this client:

  • Every provide is a snapshot unless --ga or SANSHAIN_GA=true is set, or autoGa: true meets a build that declares trunk or a tag. The client does no git or branch detection.
  • With autoGa: true, a trunk or tag build is GA. The token's user then needs the releaser role, and a changed spec without a version bump is refused with 409 immutable_ga and a proposed version. SANSHAIN_GA=false keeps such a build a snapshot.
  • --trunk / SANSHAIN_TRUNK marks a trunk build, and --tag / SANSHAIN_TAG a sanshain-branch build. On provides and requires the stream is sent with the call. On the catalog push only trunk is sent.
  • If both are declared, the client warns ⚠ trunk and tag are mutually exclusive - this build is recorded in neither and sends neither. The build still counts as declaring a stream, so autoGa makes its provide GA. With strict: true the command fails before any request with ✗ strict: trunk and tag are mutually exclusive - this build is recorded in neither.
  • A retire never carries a stability or a stream.

Origin

A provide carries the origin of the build. The fields, the runner variables and their order are in CI integration. This client reads them as follows:

  • The flags are --build-url, --change-url, --tickets and --note. They are given before the command.
  • The variables are SANSHAIN_BUILD_URL, SANSHAIN_CHANGE_URL, SANSHAIN_TICKETS and SANSHAIN_NOTE.
  • If neither gives a value, the runner's variables fill the two URLs on GitHub Actions, GitLab CI and Jenkins. Nothing is read from git.
  • The conanfile.py helper reads only the environment.
  • Only provides carry the origin. Retires, requires and catalog pushes do not, and only fields with a value are sent. The client does not check the service's limits.
  • A service before 2.9.0 refuses the fields. The client prints ⚠ Sanshain Service before 2.9.0 does not take the build's origin; providing without it on standard error and sends the provide again without them. This repeats for each provide and never fails the build, not even in strict mode.

Annotations

What annotations are, their scopes and limits is in sanshain.yaml. This client checks that each entry has exactly the strings scope (version or system), name and value. A violation fails and names the entry, for example annotations[0] (requirements): missing 'value'. An extra key is an unknown field. The service checks the limits.

  • {{NAME}} is a placeholder when NAME is only letters, digits and _. Anything else in double braces ({{ A }}, {{a-b}}) is literal text.
  • A placeholder takes its value from --set NAME=value, else from SANSHAIN_SET_NAME. The value is everything after the first =. A --set without = or without a name is a usage error: argument --set: expected NAME=value, got '<arg>' (exit code 2). The helper has no flags and reads SANSHAIN_SET_NAME only.
  • A placeholder counts as filled only with a non-empty value. An entry with an unfilled placeholder is left out with a warning, and the other entries are still sent: ⚠ annotation 'requirements' left out: {{ID}} is not set (--set ID=… or SANSHAIN_SET_ID). The helper's text names only (SANSHAIN_SET_ID). With strict: true this fails the command before any request, also for require and catalog.
  • A provide sends every entry. A require, a bundle and the catalog push send only the scope: system entries. A retire sends none.
  • A service before 2.13.0 refuses them. The client prints ⚠ Sanshain Service before 2.13.0 does not take annotations; sending without them once on standard error, sends the call again without them, and sends none for the rest of the command. This never fails the build, not even in strict mode. 
sanshain-conan --set AREA=payments --set ID=REQ-42 provide
# or
SANSHAIN_SET_AREA=payments SANSHAIN_SET_ID=REQ-42 sanshain-conan provide

Caching

  • Provides are not cached: each one uploads, and the server's no-op answers identical bytes.
  • The require command keeps each answer's ETag in .sanshain-cache/state.json. That path is relative to the working directory, not to sanshain.yaml. On the next run the client sends the ETag as If-None-Match, but only while the output file is there: a missing file is fetched again with a 200.
  • The key is <serviceName>|<version>|<METHOD>|<path> for a single endpoint and <serviceName>|<version>|bundle for a bundle. With format set, |format=<format> is appended, and then always |out=<outputDirectory> (as written in sanshain.yaml, with forward slashes), so the same endpoint required into two directories is fetched for each. 
{
  "requires": {
    "user-service|1.2.0|GET|/api/v1/users|out=gen": {
      "etag": "\"sha256:def456...\"",
      "last_fetched": "2026-04-25T12:00:00+00:00"
    }
  }
}
  • An entry is written after a successful answer that carries an ETag.
  • On 304 the client prints ⏭ <serviceName> spec unchanged (304), skipping code generation. and leaves the output file as it is.
  • An unreadable or broken state file is ignored, and the client starts fresh.
  • The conanfile.py helper keeps no state file and always downloads.

Strict mode and best effort

Strict mode is switched on only by strict: true in sanshain.yaml. Best effort is switched on by --best-effort, SANSHAIN_BEST_EFFORT (true or 1) or bestEffort: true; the helper reads only the field. Strict wins: best effort never softens a strict failure.

Without strict, missing configuration only skips, with a warning:

  • ⚠ No serviceName configured. Skipping provide. Set strict: true to fail in this case. (also Skipping require.)
  • ⚠ No provide configuration found in sanshain.yaml. Skipping. Set strict: true to fail in this case.
  • ⚠ No specification files found to provide. Skipping. Set strict: true to fail in this case.
  • ⚠ No requires configured in sanshain.yaml. Skipping. Set strict: true to fail in this case.
  • No catalogInfo in sanshain.yaml - skipping catalog. (exit code 0)

With strict: true the command fails (exit code 1) on:

  • The missing configuration above: serviceName is required (in sanshain.yaml or via environment), No 'provide' section in config, No specification files found to provide., No requires configured in sanshain.yaml, strict: sanshain.yaml has no catalogInfo. The catalog command checks only serviceName and catalogInfo.
  • An unknown field. The report ends in rejected (strict).
  • Both trunk and tag declared, before any request.
  • An annotation left out, before any request: ✗ strict: annotation '…' left out: ….
  • A Sanshain-Warning header. Every header line is printed as ⚠ <text> on every call; under strict the command then fails with ✗ strict: Sanshain warned: <text> (the first warning of that call). If the call had failed as well, its own error is printed first.
  • A catalog push that Sanshain did not record and gave no reason for: strict: Sanshain did not record <path>.

Best effort turns failed calls (a refusal, a server error, a network error) and a missing spec or catalogInfo file into warnings, and the command exits 0:

  • On provide, a missing spec file (File not found: <path>), a 409 or any other failed call skips that entry, and the client goes on with the next. A failed call prints Error: <error> and Continuing (best effort).
  • On require, a failed entry prints Error requiring <serviceName>: <error> and Continuing (best effort), and the client goes on with the next entry.
  • On catalog, a failed push prints ⚠ <error> and Continuing (best effort).

Best effort never softens a configuration error: an unreadable or invalid sanshain.yaml, a refused 1.x field and an unsupported provide apiType included, fails with Error: <error> and exit 1 before any request.

Failure modes

The only exit codes are 0 (success, skip, best effort), 1 (failure) and 2 (usage error). A failed call is printed as ✗ <message> or Error: <message>. In every quoted server body, characters outside printable ASCII become ?, and the body is cut after 1000 characters.

The conanfile.py helper

Sanshain(self, config_path=None) is built inside a recipe method. Without config_path it loads sanshain.yaml from the recipe's export-sources folder, else from the recipe folder. Relative paths in the file are resolved against the folder the file was loaded from. A conan install carries no plugin flags, so the helper reads only the environment:

  • SANSHAIN_URL and SANSHAIN_TOKEN;
  • SANSHAIN_GA, SANSHAIN_TRUNK and SANSHAIN_TAG;
  • the origin variables and the runner's variables;
  • SANSHAIN_SET_NAME.

Best effort comes only from bestEffort: true; SANSHAIN_BEST_EFFORT is not read. There is no --insecure.

  • Construction reads the file and decides the stream, stability, origin and annotations once. A configuration error raises, after the unknown-field report as Conan warnings. Under strict, both streams declared or an annotation left out raises StrictError here, before any request.
  • require() downloads every requires entry like the command, but keeps no ETag state file. Call it in generate(), so conan install . prepares the specs and the native build needs no Conan. A failed entry logs Sanshain: Error requiring <serviceName>: <error> and raises. With bestEffort: true it warns Sanshain: Continuing (best effort) and goes on.
  • provide() provides and retires like the command and logs Sanshain: Successfully provided spec(s), without the per-file summary. A missing spec file raises unless bestEffort is set. A failed call (a 409 included) logs Sanshain: <error> and raises; with bestEffort: true it warns Sanshain: <error> and Sanshain: Continuing (best effort) and goes on with the next entry. Providing is a publish step, so run it from the CLI in CI after the tests (sanshain-conan provide), not in a recipe method.
  • catalog() pushes catalogInfo. A failed push raises, or with bestEffort: true warns Sanshain: <error> and Sanshain: Continuing (best effort).
  • The helper has no skip checks for a missing serviceName, provides or requires. Without provides, provide() logs Sanshain: No 'provide' configuration found. Without requires, require() does nothing.
  • Messages go to Conan's output with the prefix Sanshain: . A Sanshain-Warning becomes output.warning and, under strict, a StrictError. The fallback warnings for an older service (origin, annotations) are printed on standard error.

CI recipes

The repository has no CI recipes of its own. Only SANSHAIN_TRUNK=true sanshain-conan catalog is its own example. The snippets below were written for this page from the options above. Keep SANSHAIN_URL in a variable and SANSHAIN_TOKEN in a secret. GA is set to true on main and left empty elsewhere, never false; with autoGa: true in sanshain.yaml the GA line can go, because trunk alone makes the provide GA.

GitHub Actions: a Producer provides after the tests, a Consumer requires during conan install

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
      SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}
      SANSHAIN_TRUNK: ${{ github.ref == 'refs/heads/main' }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install conan sanshain-conan
      - run: conan install .          # generate() calls Sanshain(self).require()
      # … build and test …
      - run: sanshain-conan provide
        env:
          SANSHAIN_GA: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}

GitLab CI

build:
  image: python:3.11
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      variables:
        SANSHAIN_TRUNK: "true"
        SANSHAIN_GA: "true"
    - when: on_success
  script:
    - pip install conan sanshain-conan
    - conan install .            # requires
    # … build and test …
    - sanshain-conan provide     # SANSHAIN_URL, SANSHAIN_TOKEN: CI/CD variables

Jenkins (multibranch): the flags go before the command

stage('Sanshain') {
  environment {
    SANSHAIN_URL   = 'https://sanshain.example.com'
    SANSHAIN_TOKEN = credentials('sanshain-token')
  }
  steps {
    sh 'pip install conan sanshain-conan'
    script {
      def stream = env.BRANCH_NAME == 'main' ? '--ga --trunk' : ''
      sh "sanshain-conan ${stream} require"
      // … build and test …
      sh "sanshain-conan ${stream} provide"
    }
  }
}

On GitLab and Jenkins the client fills the build and change URL from the runner's variables by itself; on GitHub Actions too. A release or hotfix pipeline sets SANSHAIN_TAG=<branch> (or --tag <branch>) instead of trunk. A trunk build can push the catalog with SANSHAIN_TRUNK=true sanshain-conan catalog.
