The Maven plugin sanshain-maven-plugin reads sanshain.yaml and runs provide, require and the catalog push as Maven goals. This page describes version 2.5.0; the source is paxel/sanshain-maven-plugin. In the option table, the Since column names the plugin version whose changelog entry introduced the option.

Install

The plugin is on Maven Central as io.github.paxel.sanshain:sanshain-maven-plugin:2.5.0. It needs Java 11 or later and Maven 3.6.3 or later, and it speaks Sanshain Service 2.x. The catalog goal and format: openapi need 2.4.0 or later, the build's origin is stored from 2.9.0, and annotations need 2.13.0 or later. Bind the goals in pom.xml: 

<plugin>
    <groupId>io.github.paxel.sanshain</groupId>
    <artifactId>sanshain-maven-plugin</artifactId>
    <version>2.5.0</version>
    <executions>
        <execution>
            <phase>initialize</phase>
            <goals>
                <goal>provide</goal>
                <goal>require</goal>
                <goal>catalog</goal>
            </goals>
        </execution>
    </executions>
</plugin>

The goal prefix is sanshain. All three goals default to the initialize phase, so required snippets are on disk before generate-sources. Keep only the goals the project needs; a goal without its part of the configuration warns and skips (see Strict mode and best effort).

Commands

Each goal is one call to Sanshain. In a project whose pom.xml declares the plugin, run a goal directly or let the bound execution run it: 

mvn sanshain:provide
mvn sanshain:require
mvn sanshain:catalog
mvn verify                      # runs the goals bound to initialize

The goals also run without a pom.xml; then name the plugin in full, for example mvn io.github.paxel.sanshain:sanshain-maven-plugin:2.5.0:provide, and sanshain.yaml is read from the current directory. Properties are Maven properties: -Dsanshain.ga=true anywhere on the command line, or the same name in the <configuration> of the plugin (the element names are in the option table).

  • provide uploads every entry of provides (and the single provide block, if present). With neither, it uploads target/openapi.yaml of the project when that file exists. An entry with retired: true retires its family instead of uploading.
  • require fetches every entry of requires. An entry with one endpoint is a single require, saved as <serviceName>_<path>_<method>.yaml (slashes of the path become underscores, the leading one is dropped); an entry with two or more endpoints is one bundle, saved as <serviceName>_bundle.yaml. A proto entry is saved with .proto (apiType: proto or grpc). The file goes to outputDirectory, default target/generated-sources/sanshain under the project; the directory is created when missing. An entry without endpoints warns No endpoints defined for service: <name> and is skipped.
  • catalog pushes the file named by catalogInfo to PUT /catalog/<serviceName> (see the catalog phase). On success it prints Catalog recorded for <system> (main+dev): N resources (dev for a build that is not trunk's) and each recorded resource.

With -Dsanshain.dry.run=true, provide and require send dry_run: the service checks everything and stores nothing, and require writes no ETag (it still writes the output file). A dry-run retire only checks the permission and logs ✓ Retire would be permitted. Nothing was retired. A dry-run catalog reads the file and sends nothing: Dry run - catalog not pushed: <path>. See dry runs for pull requests.

Fields of the 1.x file are refused by name before any call, each with a migration hint: timeout (requires resolve at once), releaseBranches, and stability on a provide (stability comes from the build, not the file), branch on a provide (the version comes from the spec file) or on a require (use an exact version), and baseVersion (GA immutability replaced it). A requires entry without version is refused the same way. The errors are listed under Invalid sanshain.yaml for Sanshain 2.0:.

Precedence

For each setting the first source that is set wins:

  • URL: -Dsanshain.url, then settings.xml <url>, then settings.xml <sanshainUrl>, then SANSHAIN_URL, then sanshainUrl, then http://localhost:8080. settings.xml beats the variable.
  • Token: SANSHAIN_TOKEN, then the settings.xml password, then -Dsanshain.token. The variable beats the property. An empty SANSHAIN_TOKEN still wins and sends no token.
  • serviceName: -Dsanshain.service.name, then SANSHAIN_SERVICE_NAME, then SANSHAIN_CLIENT_NAME, then serviceName or clientName in the file (if both are written, the later one in the file wins).
  • Stability: -Dsanshain.ga (true or false), then SANSHAIN_GA unless it is empty, then autoGa: true with a declared stream, then snapshot. A non-empty SANSHAIN_GA that is not true or 1 means snapshot and so also overrides autoGa.
  • Stream: trunk is -Dsanshain.trunk when set (so -Dsanshain.trunk=false switches SANSHAIN_TRUNK=true off), else SANSHAIN_TRUNK. The tag is -Dsanshain.tag unless empty, else SANSHAIN_TAG.
  • Best effort, compression, insecure, combine: the property, then the variable, then the file, then the default. A set variable decides both ways: true or 1 (trimmed, any case) is on, any other value, empty included, is off and overrides the file. Combine is first decided per provides entry.
  • Strict: -Dsanshain.strict when set (true or false), then strict in the file, then off. There is no variable.
  • Origin: per field, the property, then the SANSHAIN_* variable, then (build and change URL only) the runner's variable. Empty values count as unset.
  • Placeholders: the Maven property NAME, then the JVM system property NAME, then SANSHAIN_SET_NAME.

When sanshain.yaml cannot be read or is invalid, the goal fails before any call; best effort does not soften it.

Stability and streams

The rule is in how stability is decided. In Maven:

  • Every provide is a snapshot unless -Dsanshain.ga=true or SANSHAIN_GA=true. The log line names it: Providing OpenAPI: <name> (stability: ga).
  • autoGa: true makes the provide GA when the build declares trunk or a tag. -Dsanshain.ga=false or SANSHAIN_GA=false keeps one build a snapshot.
  • -Dsanshain.trunk=true or SANSHAIN_TRUNK=true marks a trunk build; provide and the require bundle send "trunk": true, a single require sends trunk=true, the catalog push sends "trunk": true.
  • -Dsanshain.tag=<branch> or SANSHAIN_TAG=<branch> marks a sanshain-branch build; provide and require send the tag, the catalog push does not.
  • Both set: the goal warns trunk and tag are mutually exclusive - this build is recorded in neither and sends neither; under strict mode it fails before any request. The build still counts as declaring a stream, so with autoGa: true its provide is GA.
  • A retire carries no stability and no stream.

Origin

Only provide carries an origin. The plugin reads -Dsanshain.buildUrl / SANSHAIN_BUILD_URL, -Dsanshain.changeUrl / SANSHAIN_CHANGE_URL, -Dsanshain.tickets / SANSHAIN_TICKETS and -Dsanshain.note / SANSHAIN_NOTE; without the first two it takes the build and change URL from the runner's variables on GitHub Actions, GitLab CI and Jenkins (the table is in CI integration). Tickets are split at commas, trimmed, and sent once each. Only fields that are set are sent; the limits are the service's to check. A service before 2.9.0 refuses the fields; the plugin warns Sanshain Service before 2.9.0 does not take the build's origin; providing without it and repeats the provide without them.

Annotations

The annotations entries are described in sanshain.yaml. This plugin fills a placeholder {{NAME}} (letters, digits and _) from the Maven property NAME, given as -DNAME=value on the command line or in .mvn/maven.config, else from a JVM system property NAME, else from SANSHAIN_SET_NAME. Properties in pom.xml are not read. An empty value does not fill the placeholder; an empty -DNAME= is still the property, so the variable is not consulted. Example: mvn verify -DAREA=payments -DID=4711.

An entry with a placeholder nobody filled is left out with annotation 'requirements' left out: {{ID}} is not set (-DID=… or SANSHAIN_SET_ID); the other entries are still sent. In strict mode the goal fails with strict: and that text, before any request. Provide sends both scopes; require, the bundle and the catalog push send only scope: system entries; a retire sends none. A dry run sends them as a real call would. A service before 2.13.0 refuses them; the plugin then warns once, Sanshain Service before 2.13.0 does not take annotations; sending without them, and repeats the call without them.

Caching

Require keeps the ETag of every answer in target/.sanshain-cache.json under the project directory (not relative to sanshain.yaml). The key is <producer>|<version>|<METHOD>|<path> for a single require and <producer>|<version>|bundle for a bundle, then |format=openapi when the entry sets format, then |out=<outputDirectory>, the output directory relative to the project directory, so the same endpoint required into two directories is written to both: 

{
  "requires": {
    "user-service|2.3.0|GET|/api/v1/users|out=target/generated-sources/sanshain": {
      "etag": "\"sha256:def456...\"",
      "last_fetched": "2026-04-25T12:00:00Z"
    }
  }
}

The next require sends it as If-None-Match. On 304 the output file is left as it is and the goal logs ⏭ user-service spec unchanged (304), skipping code generation. The entry is written after a 200 that carries an ETag, never on a dry run. mvn clean removes the file; so does deleting it. An unreadable file is replaced. When the output file is missing, the require is sent without If-None-Match and the answer is written again.

Provides are not cached: every provide uploads, and the service treats byte-identical content as a no-op.

Strict mode and best effort

Strict mode is on with -Dsanshain.strict=true, <strict>true</strict> in the plugin configuration, or strict: true in the file. It changes:

  • Missing configuration fails instead of warning. Without strict the goal warns <message> Skipping. Set sanshain.strict=true to fail in this case. and succeeds. The messages are serviceName is required (either in pom.xml or sanshain.yaml), No specification files found to provide. Configure provide in sanshain.yaml or disable sanshain.strict. and No requires configured in sanshain.yaml. For catalog, a missing catalogInfo warns No catalogInfo in sanshain.yaml - skipping catalog. and under strict fails with strict: sanshain.yaml has no catalogInfo.
  • Unknown fields fail: the cat that names them says rejected (strict) instead of ignored.
  • Every Sanshain-Warning fails the goal after the call with strict: Sanshain warned: <first warning>. Without strict each warning is printed as a Maven warning and the build goes on. A catalog push the service did not record and gave no reason for warns Sanshain did not record <path>.
  • Trunk and tag together fail with strict: trunk and tag are mutually exclusive - this build is recorded in neither.
  • An annotation left out fails with strict: annotation '…' left out: ….

Best effort is on with -Dsanshain.bestEffort=true, <bestEffort>true</bestEffort>, SANSHAIN_BEST_EFFORT=true or bestEffort: true. A failed call (a refusal, a server error, a network error), an unreadable or missing spec file and a combining error become a warning, Sanshain goal failed (best effort): <message>, and the goal goes on with the next entry: provide and require apply it per entry. Missing configuration warns Sanshain goal skipped (best effort): <message>; under strict it fails. Best effort never softens configuration errors: an unreadable or invalid sanshain.yaml (1.x fields included), an unsupported apiType, and the strict failures on missing configuration, unknown fields, warnings, trunk and tag, and annotations.

settings.xml

The token and the URL can live in Maven's settings.xml, outside the repository. The server whose <id> equals sanshain.serverId (default sanshain) is read: <password> is the token, <configuration><url> or, when that is missing, <configuration><sanshainUrl> is the URL. <username> is not read. 

<settings>
  <servers>
    <server>
      <id>sanshain</id>
      <password>san_abc123...</password>
      <configuration>
        <url>https://sanshain.example.com</url>
      </configuration>
    </server>
  </servers>
</settings>

The URL from settings.xml beats SANSHAIN_URL; the token from it is beaten by SANSHAIN_TOKEN (see Precedence).

Combining

Sanshain takes one document per provide. With combining on, the default, the plugin inlines a multi-file spec before the upload:

  • OpenAPI and AsyncAPI: every $ref to a local file, relative to the file that contains it, is replaced by that file, or by the part a fragment names (dto.yaml#/components/schemas/User). References that start with #, http:// or https:// stay as written, also inside an inlined file, where a #/… reference then points into the combined document.
  • Proto: every import "x.proto"; (also public and weak) of a file that exists relative to the importing file is inlined, with the imported file's syntax and package lines removed. Imports that are not local files, such as google/protobuf/timestamp.proto, stay.
  • A cycle fails with Circular dependency detected: a.yaml -> b.yaml -> a.yaml (full paths); a missing file with Referenced file does not exist: <path>.

A combined OpenAPI or AsyncAPI document is written out again: a .json file as JSON, everything else as YAML, without the original comments and layout, also when it has no reference. Switching combining on or off therefore changes the uploaded bytes, and a GA version only accepts its own bytes again; keep the setting fixed for a version line. Switch it per entry with combine on a provides entry, or for the build with -Dsanshain.combine, SANSHAIN_COMBINE or combine in the file. Line endings are sent as LF either way.

Multi-module builds and parent POMs

Each module reads the sanshain.yaml in its own directory. A company parent POM can carry the plugin so that every module runs the goals, with best effort so that a module without Sanshain, or a service that is down, does not stop the build: 

<build>
    <plugins>
        <plugin>
            <groupId>io.github.paxel.sanshain</groupId>
            <artifactId>sanshain-maven-plugin</artifactId>
            <version>2.5.0</version>
            <executions>
                <execution>
                    <phase>initialize</phase>
                    <goals>
                        <goal>provide</goal>
                        <goal>require</goal>
                    </goals>
                </execution>
            </executions>
            <configuration>
                <bestEffort>true</bestEffort>
            </configuration>
        </plugin>
    </plugins>
</build>
  • A module without sanshain.yaml and without a service name warns and skips, with or without best effort; strict mode would fail it.
  • <bestEffort> in the configuration is the property, so it beats SANSHAIN_BEST_EFFORT and the file. To leave the choice to the modules, set <sanshain.bestEffort>true</sanshain.bestEffort> in the parent's <properties> or put the configuration in <pluginManagement> instead.
  • A module opts out with <sanshain.skip>true</sanshain.skip> in its <properties>, or skips one goal with sanshain.provide.skip or sanshain.require.skip.
  • Add catalog to the goals only when the service is 2.4.0 or later; a module without catalogInfo warns and skips it.

Generating code with openapi-generator

Require runs in initialize, so a generator in generate-sources reads its output. For an AsyncAPI Producer, format: openapi delivers the payload schemas as OpenAPI. The output file name does not change with the format; to keep both forms, list the entry twice with different output directories: 

requires:
  - serviceName: order-events
    apiType: asyncapi
    version: 1.4.0
    outputDirectory: target/generated-sources/sanshain/order-events
    endpoints:
      - method: SUB
        path: orders
      - method: SUB
        path: payments
  - serviceName: order-events
    apiType: asyncapi
    format: openapi
    version: 1.4.0
    outputDirectory: target/generated-sources/sanshain/order-events-openapi
    endpoints:
      - method: SUB
        path: orders
      - method: SUB
        path: payments

The consumer's pom: require, then generate Spring models from the bundle

<build>
    <plugins>
        <plugin>
            <groupId>io.github.paxel.sanshain</groupId>
            <artifactId>sanshain-maven-plugin</artifactId>
            <version>2.5.0</version>
            <executions>
                <execution>
                    <phase>initialize</phase>
                    <goals>
                        <goal>require</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
        <plugin>
            <groupId>org.openapitools</groupId>
            <artifactId>openapi-generator-maven-plugin</artifactId>
            <version>7.8.0</version>
            <executions>
                <execution>
                    <phase>generate-sources</phase>
                    <goals>
                        <goal>generate</goal>
                    </goals>
                    <configuration>
                        <inputSpec>${project.build.directory}/generated-sources/sanshain/order-events-openapi/order-events_bundle.yaml</inputSpec>
                        <generatorName>spring</generatorName>
                        <generateApis>false</generateApis>
                        <output>${project.build.directory}/generated-sources/openapi</output>
                        <modelPackage>com.example.orders.events.model</modelPackage>
                    </configuration>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>

For an OpenAPI Producer point inputSpec at <outputDirectory>/<serviceName>_bundle.yaml when the entry lists two or more endpoints; the bundle carries each shared schema once, so the generator emits no duplicate classes. A single endpoint is <outputDirectory>/<serviceName>_api_v1_users_{id}_GET.yaml for GET /api/v1/users/{id}. A 304 leaves the file untouched, so the generator sees the same input.

CI recipes

One build covers a Producer and a Consumer: provide and require run in the same execution, the ga switch only affects provide, and trunk records the requires' pins in the main graph. Set the token as a secret, never in the file. The plain form: 

export SANSHAIN_URL=https://sanshain.example.com
export SANSHAIN_TOKEN=san_abc123...
export SANSHAIN_BEST_EFFORT=true          # optional, don't fail on server errors
mvn verify

GitHub Actions: trunk and GA on main, snapshot elsewhere

- name: Build
  run: mvn -B verify
  env:
    SANSHAIN_URL: ${{ secrets.SANSHAIN_URL }}
    SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}
    SANSHAIN_TRUNK: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}
    SANSHAIN_GA: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}

The empty value off main matters: SANSHAIN_GA=false would be an explicit snapshot and override autoGa. With autoGa: true in sanshain.yaml, drop the SANSHAIN_GA line; the trunk switch makes the provide GA. A Consumer-only project needs only the trunk line.

GitLab CI

build:
  script:
    - mvn -B verify
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      variables:
        SANSHAIN_TRUNK: "true"
        SANSHAIN_GA: "true"
    - when: on_success

SANSHAIN_URL and SANSHAIN_TOKEN come from the project's CI/CD variables (token masked). The build and merge request URLs are read from GitLab's own variables.

Jenkins (multibranch, declarative)

pipeline {
  agent any
  environment {
    SANSHAIN_URL   = 'https://sanshain.example.com'
    SANSHAIN_TOKEN = credentials('sanshain-token')
  }
  stages {
    stage('Build') {
      when { not { branch 'main' } }
      steps { sh 'mvn -B verify' }
    }
    stage('Trunk build') {
      when { branch 'main' }
      steps { sh 'mvn -B verify -Dsanshain.trunk=true -Dsanshain.ga=true' }
    }
  }
}

A pull request pipeline can check a changed spec first with mvn -B verify -Dsanshain.dry.run=true; a 409 names the version to publish as. Release and hotfix pipelines set SANSHAIN_TAG=<branch> instead of the trunk switch.
