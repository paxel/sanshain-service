sanshain is the npm package for Node builds: a CLI, a library for Node code and a composite GitHub Action, version 2.6.0, from paxel/sanshain-js. It reads sanshain.yaml and calls provide, require and catalog. This page covers what this client reads, its defaults and how it behaves. The Since column in the options table gives the client version each option arrived in.

Install

npm install --save-dev sanshain

The package installs one command, sanshain (run it as npx sanshain or from a package.json script). It needs Node 20 or later: that is the version the client's CI tests against, and the floor of the commander 14 library it uses. The package declares no engines field, so npm does not enforce this.

To fetch the pinned snippets before every build, the repository suggests a prebuild script. npm run build runs it first: 

"scripts": {
  "prebuild": "sanshain require",
  "build": "tsc"
}

Commands

npx sanshain provide                 # snapshot
npx sanshain provide --ga            # GA
npx sanshain provide --trunk         # or --tag R1
npx sanshain provide --dry-run       # validate only, stores nothing
npx sanshain require
npx sanshain require --dry-run
npx sanshain catalog
npx sanshain catalog --trunk
  • provide uploads every entry of provide and provides, in order, under the version written in the spec file. An entry with retired: true retires that API family instead (see The provides section).
  • require downloads each requires entry into its outputDirectory. The directory is created when it is missing.
  • catalog pushes the Backstage file named by catalogInfo (see The catalog phase). It has no --dry-run.

Options other than --dry-run belong to the program. They work before or after the subcommand: npx sanshain --trunk provide and npx sanshain provide --trunk do the same thing. --dry-run belongs to provide and require, so it goes after the subcommand. -V, --version prints the version; -h, --help lists the options.

0.1.0 is the first version the changelog covers, so options marked 0.1.0 have been there from the start. A — in the Since column means the changelog does not name the option. Boolean variables are on for true or 1, trimmed and in any case; any other value is off.

Fields of the 1.x branch model stop the command before any request, each with an error that names the field and says what replaces it:

  • branch: top level, in a provide entry or in a requires entry (use an exact version pin);
  • timeout: top level or in a requires entry (resolution is immediate);
  • baseVersion in a provide entry (the version comes from the spec file);
  • stability in a provide entry (use --ga or SANSHAIN_GA);
  • releaseBranches (use --ga, SANSHAIN_GA=true or autoGa: true).

Any other field the client does not know (for example a typo such as catalogInf, or a serviceName inside a provide entry) is reported once on stderr and ignored. See Failure modes.

Stability and streams

The rule itself is in How stability is decided. In this client:

  • Every provide is a snapshot unless --ga or SANSHAIN_GA=true is set, or autoGa: true meets a build that declares trunk or a tag. There is no git or branch detection.
  • --trunk / SANSHAIN_TRUNK marks a trunk build. --tag <branch> / SANSHAIN_TAG marks a sanshain-branch build. Provide and require send it. A single-endpoint require sends it as a query parameter; a bundle sends it in the body.
  • catalog sends only trunk. A tag is not sent, so a tag build's push records the dev graph only.
  • Trunk and a tag together: the client prints trunk and tag are mutually exclusive - this build is recorded in neither and sends neither. It still counts as a declared stream, so autoGa makes such a provide GA. Under strict mode the command fails before any request.
  • A retire sends no stability and no stream.

Origin

Every provide, including a dry run, carries the origin fields that are known: --build-url / SANSHAIN_BUILD_URL, --change-url / SANSHAIN_CHANGE_URL, --tickets / SANSHAIN_TICKETS and --note / SANSHAIN_NOTE. The two URLs default to the runner's variables on GitHub Actions, GitLab CI and Jenkins; the table is in Why: the origin of a build. Tickets are split at commas, trimmed, and duplicates are dropped. The client does not check the service's limits; the service does. Require, catalog and retire carry no origin. Nothing is read from git. 

npx sanshain --tickets ORD-7,ORD-9 --note "Adds the users endpoint" provide

Annotations

The file side is in Annotations. This client checks before any request that every entry has scope (version or system), name and value, all strings. A violation names the entry.

  • A placeholder is {{NAME}}, where NAME is letters, digits and _. Anything else between double braces stays literal text. Placeholders are filled in value only.
  • The value comes from --set NAME=value, else from SANSHAIN_SET_NAME (exact case). --set splits at the first =. Without one it is refused: expected NAME=value, got '<arg>', exit 1.
  • An entry with a placeholder that is still empty is left out, and the others are sent: annotation 'requirements' left out: {{ID}} is not set (--set ID=… or SANSHAIN_SET_ID). Under strict mode this fails the command before any request, also with best effort. The check covers every entry, also on require and catalog, which send only the system entries.
  • provide (also with --dry-run) sends every entry. require, its bundles and catalog send only scope: system entries. A retire sends none.
  • A service before 2.13.0 refuses annotations. The client then repeats the call without them, sends none for the rest of the run, and warns once: Sanshain Service before 2.13.0 does not take annotations; sending without them. Strict mode does not fail on this warning. 
npx sanshain --set AREA=7 --set ID=42 provide
SANSHAIN_SET_AREA=7 SANSHAIN_SET_ID=42 npx sanshain provide

Caching

  • Provides always upload. The service treats identical bytes as a no-op.
  • Requires keep each ETag in node_modules/.cache/sanshain/state.json. That path is relative to the working directory, not to sanshain.yaml. The key is <producer>|<version>|<METHOD>|<path> for a single endpoint and <producer>|<version>|bundle for a bundle, followed by |openapi when format is set and by |out=<outputDirectory> (as written in sanshain.yaml, with forward slashes), so the same endpoint required into two directories is fetched for each. Each entry holds etag and last_fetched.
  • The stored ETag goes out as If-None-Match, but only while the output file is there: a missing file is fetched again with a 200. On 304 the client prints <producer> spec unchanged (304), skipping code generation. and leaves the file as it is. The ETag is written after a 200 that carried one, except on a dry run.
  • A require --dry-run writes nothing: no output directory, no file and no ETag. It prints Dry run - <file> not written to <outputDirectory>.
  • A corrupt state file is replaced silently. A provides section written by clients before 2.4.0 is kept and ignored.

Strict mode and best effort

Strict mode is on with strict: true or SANSHAIN_STRICT=true. There is no flag. Without it, missing configuration is a warning and exit 0:

  • No serviceName configured. Skipping provide. Set strict: true to fail in this case. (the same for require and catalog)
  • No provide configuration found in sanshain.yaml. Skipping. Set strict: true to fail in this case.
  • No specification files found to provide. Skipping. Set strict: true to fail in this case.
  • No requires configured in sanshain.yaml. Skipping. Set strict: true to fail in this case.
  • No catalogInfo in sanshain.yaml - skipping catalog.

Under strict mode each of these exits 1, and so do the following:

  • Missing configuration: serviceName is required (in sanshain.yaml or via SANSHAIN_SERVICE_NAME), No provide section in sanshain.yaml, No specification files found to provide., No requires configured in sanshain.yaml, strict: sanshain.yaml has no catalogInfo. The catalog command checks only serviceName and catalogInfo.
  • Any Sanshain-Warning: strict: Sanshain warned: <first warning>, after the call. A catalog file Sanshain did not record counts as a warning, with Sanshain did not record <path> when the service sent no text.
  • Trunk and a tag together, before any request: strict: trunk and tag are mutually exclusive - this build is recorded in neither.
  • An annotation with an unfilled placeholder, before any request: strict: annotation '…' left out: ….
  • Unknown fields in sanshain.yaml: the report ends in rejected (strict). Under best effort only when the file otherwise loads or SANSHAIN_STRICT=true is set; a file that does not load is broken (see below), and the report ends in ignored.

Best effort is on with --best-effort, SANSHAIN_BEST_EFFORT=true or bestEffort: true. It softens failed calls: a refusal, a server error, a network error, and a missing spec file or catalogInfo file; with the flag or the variable also a missing or broken sanshain.yaml (below). A failure is printed as Error providing spec: …, Error during require: …, Error requiring <producer> <version>: … or Error pushing catalog: …, followed by Continuing (best effort), and the command exits 0.

  • The strict failures above are never softened, and neither are unknown fields under strict in a file that otherwise loads.
  • provide and require apply it per entry: a failed entry is skipped and the next one runs. After a failed provide the closing Successfully provided spec(s). is not printed.
  • A sanshain.yaml that is missing, cannot be read or does not load (invalid YAML, 1.x fields, invalid entries, an unsupported apiType) fails the command before any request without best effort; a missing file is named, as in Error providing spec: Configuration file not found: <path>. With --best-effort or SANSHAIN_BEST_EFFORT=true it prints the same line, then Continuing (best effort), calls nothing and exits 0 (since 2.6.0; before, it printed Warning loading config: <error> and a skip notice). Such a file's own bestEffort and strict do not count; SANSHAIN_STRICT=true makes it fail also with best effort.

Without strict mode, each warning Sanshain sends is printed on its own line, starting with a warning sign, and the build carries on.

Failure modes

Exit codes are 0 or 1. Every exit 1 below becomes a printed failure and exit 0 under best effort, except where the row says otherwise. Messages printed by provide start with Error providing spec: ; the other commands use their prefixes from the previous section.

Situation What the client does
409 on provide (version rules) Provide rejected by the version rules (409): <reason>, then Publish as <proposed version> — update info.version in <file> (for proto: the '// sanshain-version:' comment). Exit 1. The client never edits the spec file.
403 Refused (403): <reason>. When the service refused for want of the releaser role, a hint follows that publishing GA needs the role, that retiring needs it or a maintainer grant, and how to publish a snapshot instead. Any other 403, such as a read-only token's (which needs scope full), shows the service's message alone. Exit 1.
404 Unknown producer or version (404): <reason> — check the pinned version in sanshain.yaml. Exit 1.
410 on require Absent endpoint (410): <reason> — the pinned version exists but deliberately does not include the requested endpoint(s). Exit 1. A bundle fails as a whole.
No token, or 401 The client does not check for a token. The service's answer is shown as Request failed with status 401: <body>. Exit 1.
Other 4xx and 5xx Request failed with status <n>: <body>. The body is cut at 1000 characters, and characters outside printable ASCII are shown as ?. Exit 1, no retry.
Network error The HTTP library's message, e.g. connect ECONNREFUSED …. Exit 1, no retry.
Pre-2.0 server After a failed call the client asks GET /version once. Below 2.0.0 the error becomes Sanshain server at <url> is <version>; this client requires Sanshain 2.x — upgrade the server.
Service too old for catalog A 404 on the catalog push becomes sanshain catalog needs Sanshain Service 2.4.0 or later (server is <version>). Exit 1.
Service too old for format: openapi format: openapi needs Sanshain Service 2.4.0 or later (server is <version>). Nothing is written. Exit 1.
Service too old for the origin (before 2.9.0) It warns Sanshain Service before 2.9.0 does not take the build's origin; providing without it and repeats the provide without the origin.
Service too old for annotations (before 2.13.0) It warns once (see Annotations) and repeats the call without them. Strict mode does not fail.
Unknown fields in sanshain.yaml It prints once on stderr sanshain.yaml: unknown field 'catalogInf' - ignored, inside a small ASCII cat, and carries on. Under strict the line ends in rejected (strict) and the command exits 1, also with best effort when the file otherwise loads.
1.x fields An error naming the field and its replacement, e.g. 'timeout' is no longer supported — Sanshain 2.0 resolves immediately (no long-polling); remove it. Exit 1, before any request, or a warning under best effort (see Strict mode and best effort).
Trunk and tag both set It warns and sends neither. Exit 0, or exit 1 before any request under strict mode.
Configuration missing or invalid Configuration file not found: <path>, Missing required field: sanshainUrl, or an error naming the entry (e.g. requires[0] (auth-service): missing 'version' — …). Exit 1, before any request, or a warning under best effort.
Unsupported apiType on a provide or a require provides[0]: unsupported apiType '<value>' — use openapi, asyncapi or proto (grpc means proto) (a require's starts requires[0] (<producer>): , a single provide entry's provide: ). Exit 1, before any request, or a warning under best effort.
Spec file missing Spec file not found: <absolute path>. Exit 1. Under best effort the file is skipped.

What it sends and writes

  • Provide posts to /provide, /provide/asyncapi or /provide/grpc (for apiType: proto). Line endings are converted to LF first. It prints Provided <system> <version> (<stability>): <n> new, <n> updated, <n> deleted endpoints. After an AsyncAPI provide it lists the harvested subscriptions. Those with drift or no publisher are printed as warnings and never fail the build.
  • Retire posts {producername, retired: true} (plus dry_run) to the family's provide endpoint. It prints the capability cleared and the trunk pins and contracts released.
  • Require uses GET /require (/require/asyncapi, /require/grpc for apiType: proto or grpc) for an entry with one endpoint. It writes <outputDirectory>/<producer>.yaml. An entry with several endpoints goes to POST /require-bundle and is written as <producer>_bundle.yaml; a bundle sends grpc as api_type: proto. Proto results end in .proto.
  • Catalog sends PUT /catalog/<serviceName> and prints Catalog recorded for <system> (main+dev): <n> resources (or (dev)) with one resource per line. A file Sanshain could not read records nothing: it is a warning and exit 0, or a failure under strict mode.
  • What it prints: the Sanshain URL in Providing …, Requiring …, Pushing catalog … and the hint for a pre-2.0 server appears without a user and password it carries (https://ci:secret@sanshain.example is printed as https://sanshain.example/). The token is never printed. Text the service sends (error messages, Sanshain-Warning values, the provide, retire and catalog answers, its version) is printed with every control character but the tab replaced by ?, so it cannot start a log line of its own or send terminal escape sequences. Both since 2.6.0.

The library

The package entry exports the client, the cache, the configuration helpers and the CLI program. The library throws errors and never exits the process; the CLI does the printing and exiting.

Export What it is
SanshainClient(baseUrl, token?, insecure = false) The HTTP client. Its methods are provide, provideAsyncApi, provideProto (payload, compression), retire(producername, apiType?, dryRun?), require(consumername, producername, version, path, method, dry_run?, api_type?, etag?, stream?, format?, annotations?), requireBundle(payload, compression, etag?, format?) and pushCatalog(systemname, catalogInfoYaml, stream?, compression, annotations?). takeWarnings() returns the Sanshain-Warning values received so far and clears them.
VersionConflictError, UnknownVersionError, AbsentEndpointError Thrown for 409 (with proposedVersion), 404 and 410.
loadConfig(path?), configBaseDir(path?), resolveStability, resolveStream, resolveStreamWithWarning, streamDeclared, resolveOrigin, fillAnnotations, parseSet, envFlag The rules the CLI applies, from loading sanshain.yaml (with the environment overrides and all checks) to stability, stream, origin and placeholders. They are documented above.
SanshainCache(cacheDir?) The require ETag store: getRequireEntry, updateRequireEntry, save, and the keys SanshainCache.requireKey and requireBundleKey.
program, StrictFailure The commander program behind the CLI, and the error type of a strict failure.

The payload and result types (ProvidePayload, ProvideResponseBody, RequireResult, Stream, Origin, Annotation and more) ship as TypeScript declarations. 

const { SanshainClient, VersionConflictError } = require('sanshain');

async function publish(spec) {
  const client = new SanshainClient(process.env.SANSHAIN_URL, process.env.SANSHAIN_TOKEN);
  try {
    const result = await client.provide({
      producername: 'orders',
      openapi_yaml: spec,
      stability: 'snapshot',
    });
    console.log(result?.version, result?.changes);
  } catch (e) {
    if (e instanceof VersionConflictError) console.error('publish as', e.proposedVersion);
    else throw e;
  }
}

The GitHub Action

The repository is also a composite Action: uses: paxel/sanshain-js@summer. It runs npx --yes --ignore-scripts sanshain@<version> <command> in working-directory and sets up no Node. The version is pinned in the Action's action.yml to a release that is on npm and raised after each release, so the CLI that runs is fixed by the Action's ref, not by the newest version on npm (since 2.6.0; before, plain npx sanshain). A project's own install is used only when it is that version; otherwise npx downloads it, without running any install scripts.

Input Required Default Becomes
command yes — provide, require or catalog
token no — SANSHAIN_TOKEN; without the input, the step's SANSHAIN_TOKEN environment
ga no '' SANSHAIN_GA: 'true' GA, 'false' snapshot even under autoGa, empty lets autoGa decide
trunk no '' SANSHAIN_TRUNK
tag no '' SANSHAIN_TAG
tickets no '' SANSHAIN_TICKETS
note no '' SANSHAIN_NOTE
working-directory no '.' The directory the CLI runs in, where sanshain.yaml is
  • A non-empty input sets SANSHAIN_GA, SANSHAIN_TRUNK, SANSHAIN_TAG, SANSHAIN_TICKETS or SANSHAIN_NOTE and replaces a variable of the same name set on the job or workflow. An empty input, the default, keeps that variable as it is.
  • Everything without an input goes through the environment of the step: the URL (SANSHAIN_URL), placeholders (SANSHAIN_SET_<NAME>), strict mode, best effort, compression, and the two origin URLs if the runner's own are not wanted. The Action has no input for --config, --dry-run, --set or --insecure; run the CLI for those.
  • The build and pull-request URLs come from GitHub's own variables. The Action has no outputs.

CI recipes

Trunk is declared on the default branch (here main), and GA only there, never as an explicit false. With autoGa: true in sanshain.yaml the GA line can go. A Producer runs provide, a Consumer require. A project with a catalogInfo adds a catalog step the same way.

GitHub Actions, a Producer with the Action

steps:
  - uses: actions/checkout@v4
  - run: npm ci
  - uses: paxel/sanshain-js@summer
    with:
      command: provide
      ga: ${{ github.ref == 'refs/heads/main' && 'true' || '' }}
      trunk: ${{ github.ref == 'refs/heads/main' }}
    env:
      SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
      SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}

GitHub Actions, a Consumer with the Action

  - uses: paxel/sanshain-js@summer
    with:
      command: require
      trunk: ${{ github.ref == 'refs/heads/main' }}
    env:
      SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
      SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}

GitHub Actions, a pull-request check with the CLI (the Action has no dry run)

  - run: npx sanshain provide --dry-run
    env:
      SANSHAIN_URL: ${{ vars.SANSHAIN_URL }}
      SANSHAIN_TOKEN: ${{ secrets.SANSHAIN_TOKEN }}
