The answers are the recordings of A team's story; where a task is not in the story, the answer is quoted from the REST API reference. Set SANSHAIN to your instance and SANSHAIN_TOKEN to a token; the recordings show the address as https://sanshain.corp.

What changed in 2.18.0

Mint a read-only token for an AI client

From a session (log in first, or use the account page), with "scope": "read_only"; full is the default for CI. 

curl -s -X POST $SANSHAIN/auth/tokens \
  -H "Authorization: Bearer $SESSION" -H "Content-Type: application/json" \
  -d '{"name":"claude-code","expires_in_days":90,"scope":"read_only"}'

Validate a spec before publishing



  
No token, nothing stored; the answer is always 200 with a verdict.

  
curl -s -X POST $SANSHAIN/validate -H "Content-Type: application/json" \
  -d "{\"api_type\":\"openapi\",\"content\":$(jq -Rs . < openapi.yaml)}"

  Check a pull request without storing anything




  

    A provide with "dry_run": true runs the version rules too (the validator does not)
    and persists nothing. Expect the same answers as a real provide: 202, or
    409 with proposed_version.
  

  
curl -f -X POST $SANSHAIN/provide \
  -H "Authorization: Bearer $SANSHAIN_TOKEN" -H "Content-Type: application/json" \
  -d "{\"producername\":\"payments\",\"stability\":\"ga\",\"openapi_yaml\":$(jq -Rs . < openapi.yaml),\"dry_run\":true}"

Publish a breaking change



  

    A removed or renamed path behind a minor bump is refused; the major the answer proposes goes
    through. With a client, the ga switch on the release pipeline does the publish.

Get the report for a release



  

    scope is dev, main or a branch name, the latter two
    optionally @<RFC 3339 instant>; /report/markdown and
    /report/isolation take the same parameter.
  

  
curl -s "$SANSHAIN/report?scope=release-2026.10" -H "Authorization: Bearer $SANSHAIN_TOKEN"

Send the git branch of a build



  

    The clients fill it from the runner; a raw curl pipeline sends it itself, with the
    pull request target when there is one.
  

  
curl -X POST $SANSHAIN/provide -H "Authorization: Bearer $SANSHAIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"producername\": \"orders\", \"stability\": \"snapshot\", \"openapi_yaml\": $(jq -Rs . < openapi.yaml),
       \"git_branch\": \"$GITHUB_HEAD_REF\", \"git_target_branch\": \"$GITHUB_BASE_REF\"}"

Get a patch proposal on a release branch



  

    Build the hotfix on release/2.6 (or hotfix/…, or with a stream tag); a
    refused provide then proposes the next patch of 2.6. Check what Sanshain makes of a
    branch name before relying on it:
  

  
curl -s -X POST $SANSHAIN/admin/settings/branch-rules/test \
  -H "Authorization: Bearer $SESSION" -H "X-CSRF-Token: $CSRF" -H "Content-Type: application/json" \
  -d '{"patterns": ["^(?<kind>release)/"], "branch": "release/2.6"}'
{"reading": {"kind": "release", "target": null}, "maintenance": true}

Find a free move for a Consumer



  
Every require names it, when there is one:

  
curl -si "$SANSHAIN/require?consumername=shop&producername=orders&version=1.5.0&path=/orders&method=GET" \
  -H "Authorization: Bearer $SANSHAIN_TOKEN" | grep -i x-sanshain-upgrade
x-sanshain-upgrade: 1.11.0

Push a Product release from the Helm pipeline



  

    After the umbrella chart is published, with a full token of a Product Maintainer; name a
    sanshain-branch when the release is cut from one.
  

  
curl -X PUT "$SANSHAIN/products/shop/chart?scope=release-2026.10" \
  -H "Authorization: Bearer $SANSHAIN_TOKEN" --data-binary @Chart.yaml
{"chart_version": "1.3.0", "outcome": "created", "members": {"added": [], "removed": [], "skipped": []}}
