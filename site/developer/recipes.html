One task per section, each with the command, the answer a 2.6.0 instance gave, and where to read more. The answers are the recordings of A team's story; where a task is not in the story, the answer is quoted from the REST API reference. Set SANSHAIN to your instance and SANSHAIN_TOKEN to a token; the recordings show the address as https://sanshain.corp.

Mint a read-only token for an AI client

From a session (log in first, or use the account page), with "scope": "read_only"; full is the default for CI. 

curl -s -X POST $SANSHAIN/auth/tokens \
  -H "Authorization: Bearer $SESSION" -H "Content-Type: application/json" \
  -d '{"name":"claude-code","expires_in_days":90,"scope":"read_only"}'

Validate a spec before publishing



  
No token, nothing stored; the answer is always 200 with a verdict.

  
curl -s -X POST $SANSHAIN/validate -H "Content-Type: application/json" \
  -d "{\"api_type\":\"openapi\",\"content\":$(jq -Rs . < openapi.yaml)}"

  Check a pull request without storing anything




  

    A provide with "dry_run": true runs the version rules too (the validator does not)
    and persists nothing. Expect the same answers as a real provide: 202, or
    409 with proposed_version.
  

  
curl -f -X POST $SANSHAIN/provide \
  -H "Authorization: Bearer $SANSHAIN_TOKEN" -H "Content-Type: application/json" \
  -d "{\"producername\":\"payments\",\"stability\":\"ga\",\"openapi_yaml\":$(jq -Rs . < openapi.yaml),\"dry_run\":true}"

Publish a breaking change



  

    A removed or renamed path behind a minor bump is refused; the major the answer proposes goes
    through. With a client, the ga switch on the release pipeline does the publish.
  

  
SANSHAIN_GA=true sanshain-go -trunk provide     # or: cargo sanshain provide --ga --trunk

Require one endpoint by hand



  

    The exact pin and one endpoint; the snippet comes back as YAML with the
    x-sanshain-* headers.
  

  
curl -g -s "$SANSHAIN/require?consumername=orders&producername=payments&version=1.0.0&path=/payments&method=POST&trunk=true" \
  -H "Authorization: Bearer $SANSHAIN_TOKEN"

Cut a release branch



  

    Needs the releaser role and a session; source and as_of are optional
    (trunk, now).
  

  
curl -s -X POST $SANSHAIN/admin/branches \
  -H "Authorization: Bearer $SESSION" -H "Content-Type: application/json" \
  -d '{"name":"release-2026.10"}'

Get the report for a release



  

    scope is dev, main or a branch name, the latter two
    optionally @<RFC 3339 instant>; /report/markdown and
    /report/isolation take the same parameter.
  

  
curl -s "$SANSHAIN/report?scope=release-2026.10" -H "Authorization: Bearer $SANSHAIN_TOKEN"

Build on a release branch

Push the catalog



  

    With catalogInfo in sanshain.yaml every client pushes on each build;
    by hand it is one PUT.
  

  
curl -s -X PUT $SANSHAIN/catalog/payments \
  -H "Authorization: Bearer $SANSHAIN_TOKEN" -H "Content-Type: application/json" \
  -d "{\"catalog_info_yaml\":$(jq -Rs . < catalog-info.yaml),\"trunk\":true}"

Ask the catalog over MCP



  

    What a client sends; in practice the assistant does this for you once the endpoint is
    configured.
  

  
curl -s -X POST $SANSHAIN/mcp \
  -H "Authorization: Bearer $SANSHAIN_TOKEN" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"describe_service","arguments":{"name":"payments"}}}'
