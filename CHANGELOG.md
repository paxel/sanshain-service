# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).


## [1.5.2] - 2026-07-23

### Added
- Branch fallback resolution (`/provide`, `/require`, endpoint history) can now be steered explicitly instead of guessing: `source_protected_branch` is a new, optional field on `/provide` and `/require` — a sticky, per-branch hint recording which protected branch (e.g. a `release/X.Y` line) this branch defers to when it has no data of its own. It takes effect the first time it is supplied for a given branch; a later, differing value from a different caller is ignored (and logged as a mismatch, tagged service/branch) rather than silently overwriting it, so different CI runs or machines can't flip-flop the effective answer — only an admin can change it afterward, via a new `GET`/`PUT /admin/services/{name}/branches/{branch}/source-protected-branch`. This replaces the previous behavior (falling back to alphabetical order over all protected branches), which had no way to distinguish which release line a given branch actually belonged to once more than one protected branch existed — a hotfix cut from an old `release/X.Y` line could silently resolve against `master`'s current, diverged API. Separately, `pull_from_branch` is a one-shot override that resolves a single request against an exact branch, bypassing `source_protected_branch` and all fallback resolution, without persisting anything — for a client whose own understanding of its lineage disagrees with what's stored. Both fields are accepted by `/require`, `/require/asyncapi`, `/require/grpc` (query parameters) and `/require-bundle` (body fields), and all of them resolve lineage through the identical chain.
- The observability log viewer now shows which service/branch a log line refers to, for `provide` and `require` events: a compact `[service/branch]` chip appears inline when the event carries that context (most other lines — auth, startup, migrations — have none and show no chip). Previously (1.5.1) every event's structured fields other than the message text were silently discarded by the log-capture layer, and neither the provide nor the require code path attached service/branch context to their log lines at INFO level in the first place, so there was no way to tell from the log stream which service/branch a given line was about.
- The full API spec for a branch can now be viewed/downloaded: a **"Download full API"** button on the services branch view reassembles the branch's stored per-endpoint specs into one document (OpenAPI merged into a single document; AsyncAPI/proto concatenated) via a new authenticated endpoint, `GET /admin/services/{name}/branches/{branch}/full-spec?api_type=…`.
- The services overview now shows each branch's **last-published time** on its branch card (or "No publishes yet" when it has never received a publishing change). The timestamp reflects the last spec change published to that branch, not merely when it was last viewed.
- The services overview now shows an amber **"Expires in Nd"** badge on a branch card when a non-protected branch is within 3 days of removal by stale-branch cleanup (computed from its last publish and the configured retention window, `branch_max_age_days`). Protected branches, which are never culled, show no badge.
- `/provide` now accepts an optional `author` field to override who gets credited in an endpoint's version history (the blame view in the endpoint YAML page), for clients — typically a CI pipeline — that publish under a shared service-account identity but know the real author of the change. Sanshain has no git access, so this is a pure, unverified client-supplied hint: an `author` override affects blame display only and never changes the audit log, which always records the real authenticated caller that made the request. Previously (1.5.1) version-history blame always showed the authenticated caller, with no way to distinguish "who published this" from "who actually wrote it."

### Fixed
- Wildcard protected-branch patterns (e.g. `release/*`) now actually protect the branches they match, and mean the same thing on both database backends. Previously (1.5.1) `is_branch_protected` compared patterns by exact string, so a wildcard pattern was accepted and exempted matching branches from stale cleanup, yet those branches were still treated as *unprotected* everywhere else — breaking changes were not rejected, per-endpoint version history was not recorded, and the endpoint fallback resolver skipped them. Pattern matching is now performed uniformly in one place rather than delegated to each backend's SQL dialect: `*` matches any sequence and `?` exactly one character, everywhere. This also removes a PostgreSQL-only hazard, where patterns were matched with SQL `LIKE` and a pattern such as `feature_x` silently treated `_` as a single-character wildcard (protecting `featureAx` as well) while SQLite did not. **Upgrade note (PostgreSQL only):** a branch that was protected *only* because an `_` in some pattern happened to match it was never really meant to be protected, and is no longer. Such a branch becomes eligible for stale-branch cleanup and will be deleted by the next sweep once it is past the retention window (`branch_max_age_days`). If any of your protected-branch patterns contain `_`, review them before upgrading — write the wildcard you actually mean (`feature*`) or add the exact branch names. Wildcard-protected branches are now also ordered first in the services overview, excluded from the stale-cleanup expiry badge, and reachable as fallback targets — `list_protected_branches` returns patterns, so the resolver previously looked for a branch literally named `release/*` and found none. Exact patterns like `main`/`master` are unchanged.
- Editing an endpoint's spec from the admin UI now counts as branch activity and advances the branch's last-published time. Previously (1.5.1) only a `provide` did, so a manually edited branch could still show a stale "last published" time and be removed by stale-branch cleanup despite the recent edit.
- Opening an endpoint's history for a branch the server never published — for example one a client *requires* but the service only *provides* on `master` — now falls back to the service's configured fallback branch, then to any protected branch, and shows **that** branch's history with a note ("Branch X has no published spec — showing history from master"). Previously (1.5.1) the history view (`/admin/endpoint-versions`) queried the exact branch only and failed with a raw "Failed to load versions: 404". Only when no branch at all has the endpoint does it now show an explicit "not available" state. (The endpoint YAML view already resolved branches this way; the history view now matches it.) The same fallback now also applies to a branch that *does* hold the endpoint's real content — e.g. a feature branch branched from `master` with identical, unchanged content — since only protected branches ever accumulate version rows; such a branch previously reported an empty history of its own instead of inheriting the real one recorded on `master`.
- The "resolved → service" link on a client's endpoint now carries the endpoint's API type, so AsyncAPI and gRPC/proto endpoints open with the correct viewer instead of defaulting to OpenAPI.
- A branch's "last updated" time (`branches.updated_at`) is now advanced only when a spec change is actually published to it, not when the branch is merely viewed. Previously (1.5.1) any read that resolved the branch — viewing an endpoint's history, listing a branch's endpoints — bumped the timestamp, with two consequences: "last activity" reflected the last *view* instead of the last *publish*, and the stale-branch cleanup (which deletes branches whose `updated_at` is older than the retention window) had its timer reset just by someone looking at the branch, so a viewed-but-unpublished branch was never culled. Viewing no longer keeps a branch alive; only a publishing change does. (A no-op re-publish of an identical spec does not advance it either, consistent with it producing no change.)
- Revoking an API token that doesn't exist (or was already revoked) now correctly returns `404` instead of silently reporting success and writing a "Revoked" audit entry regardless.
- Opening an endpoint's history for a *protected* branch that holds the endpoint but has no recorded versions of its own no longer shows a different protected branch's history under that branch's name. A protected branch is authoritative for its own line, so it never inherits another's history — matching the rule the endpoint YAML view already applied.

### Changed
- The services overview ("server" browsing view) now only lists a service/branch if it actually serves something. Providing an OpenAPI spec with no `paths` is still accepted (a branch is created, and a client's dependency report still works), but such an empty branch — and a service whose branches are *all* empty — no longer appears in the services list or its branch cards, since there is nothing there to browse. Admin management (branch/service deletion, the audit-log dependent views) is unaffected and still sees every branch, including empty ones. The dependency graph already excluded empty branches (it is built from actual endpoint dependencies) and needed no change.
- Branches in the services overview are now ordered deterministically — protected branches (e.g. `master`/`main`) first, then by most recent publish (newest first), then alphabetically. Previously (1.5.1) the per-service branch list came back in an unspecified order (SQLite `GROUP_CONCAT`), so it could look unsorted and vary between requests.
- Viewing a branch no longer creates a "Generated report" audit entry. The branch view fetches `GET /report` to render, and that read is no longer audited — so the audit timeline stops filling with a report row on every view. Explicit report *exports* (`GET /report/markdown`, `/report/isolation`, `/report/merged`) are still audited. Previously (1.5.1) each branch view added a `REPORT`/`READ` audit entry.
- A `provide` that results in no endpoint changes (re-uploading an identical spec) no longer creates a `PROVIDE_SPEC` audit entry. Previously (1.5.1) every non-dry-run provide was audited even when it changed nothing (`+0, ~0, -0`), cluttering the audit timeline. Applies to OpenAPI, AsyncAPI, and gRPC/proto provides.

### Security
- The audit log (`GET /admin/observability/audit-logs` and its CSV export) now requires admin privileges. Previously (1.5.1) both were reachable by any authenticated user — the routes lived under `/admin/` by naming convention only; the actual middleware (`authenticated_auth`) accepted any valid session, not just admins. A non-admin, regular user could view the full audit trail — every provide/require, token create/revoke, branch/service deletion, and settings change, across all users. The observability stats and raw log-stream views remain open to any authenticated user, unchanged.
- API token creation and revocation audit entries ("Created an API token" / "Revoked an API token") no longer include the token's name or its internal ID. Previously (1.5.1) both were logged in plain text (`Created API token 'name' with ID '...'`); since audit log entries are permanent, a token name the creator considered private, or the ID itself, had no way to be redacted after the fact. The repository layer no longer returns a revoked token's name at all, so the value cannot be reintroduced into a log by a future caller.
- Service and branch names are now HTML-escaped when rendered in the services overview, and its buttons bind their handlers as event listeners instead of embedding those names in generated `onclick` attributes. Service and branch names arrive from client `/provide` payloads and are not validated, so a name containing markup was previously (1.5.1) interpolated raw into the page — letting any client holding an API token store script that ran in an admin's browser when the affected service was browsed.
